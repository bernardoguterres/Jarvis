# Jarvis — Architecture

This document derives from and is subordinate to `CLAUDE.md` (the authoritative project profile). If anything here conflicts with `CLAUDE.md`, `CLAUDE.md` wins.

## 1. Technology Stack

* **Frontend**: React, TypeScript, Vite.
* **Backend/controller**: Python, FastAPI.
* **Persistence**: SQLite, SQLAlchemy, Alembic migrations.
* **Agent harness**: Hermes Agent, via its local authenticated API.
* **Primary reasoning model**: currently GPT-5.6 Terra, via OpenAI Codex OAuth against Bernardo's ChatGPT subscription — configured entirely on the Hermes side, never as a model string the backend sends (see §7a). Model-independent by construction, not just by intent.
* **Speech-to-text**: local faster-whisper (initial).
* **Text-to-speech**: Edge TTS (initial); ElevenLabs is an optional later upgrade.
* **Interface**: local browser application (HUD).
* **Testing**: pytest (backend), frontend unit tests, type-checking, production builds.
* **Version control**: Git.

### Explicitly excluded for now

Tauri, Electron, Docker, a VPS, cloud database storage, a local LLM, Kubernetes, microservices, continuous microphone recording, email/calendar write access, unnecessary framework replacements. A technology is reconsidered only when a demonstrated requirement cannot be met cleanly with the current stack.

## 2. System Flow

```
User
  → React HUD
  → Jarvis FastAPI Controller
  → domain router and context builder
  → local Jarvis database
  → Hermes local API
  → selected reasoning model
  → response
  → text-to-speech
  → HUD and spoken reply
```

Hermes supplies the agent loop, tools, session capabilities, skills, and integrations.

### The Jarvis Controller owns:

* active-domain state
* model-independent memory
* structured personal records
* context retrieval
* permissions
* export and restoration
* the HUD event stream
* model selection
* audit records

Hermes's built-in memory is **not** the authoritative repository for Bernardo's history — the Jarvis Controller's local database is.

## 3. Domains as Context Spaces

BODY, MIND, PEOPLE, PATH, BUILD, LIFE are **context spaces inside one agent**, not six separate agents or six Hermes profiles. A single domain router determines the active domain (from explicit selection or natural-language aliasing) and the context builder assembles domain-scoped context before invoking Hermes/Claude. Cross-domain context inclusion must be explicit and justified in the context-builder logic — never a default join across all domains. A conversation may also have *no* active domain at all — the general Jarvis conversation opened from the core itself (§6.3, §9h, D75) — which is a scope with no domain assigned, not a seventh entry in this list.

## 4. Data Ownership and Layout

Application source (Git repo) and personal data are strictly separated.

Personal data lives under a configurable `JARVIS_DATA_DIR`, default `~/JarvisData`:

```
JARVIS_DATA_DIR/
  database/jarvis.sqlite
  documents/
  domain-summaries/
  skills/
  configuration/
  backups/
  exports/
```

Hermes may keep its own runtime state in its supported profile location; Jarvis's exporter includes an official Hermes profile export rather than relying on undocumented internal copying.

### Rules

* Never store authoritative personal data in browser localStorage.
* Never commit personal data or secrets to Git.
* Never reset or overwrite an existing database automatically.
* Never silently discard unknown schema versions.
* Never treat generated embeddings as the only copy of information — original text/structured records are authoritative; indexes/embeddings are derived and rebuildable.

## 5. Export / Import / Backup Mechanics (implemented, Phase 2)

### 5.1 Export archive format

`jarvis-export-YYYYMMDD-HHMMSS.zip`, built by `backend/app/export_service.py`, contains:

* `manifest.json` — export-format version, app version, schema revision (the Alembic `alembic_version` read directly off the source database), creation timestamp (UTC), non-identifying platform info (OS/arch/Python version — no hostname or username), included/excluded components, a reserved-but-unpopulated `hermes_profile_export` block (see below), `secrets_included: false`, and a `files` list with a SHA-256 checksum and size for every payload file. This manifest *is* the checksum manifest — there is no separate `checksums.json`.
* `database/jarvis.sqlite` — a consistent snapshot taken via SQLite's own online backup API (`sqlite3.Connection.backup()`), never a raw filesystem copy of a possibly-open file.
* `documents/`, `domain-summaries/`, `skills/`, `configuration/` — included only when non-empty, walked recursively, excluding `.env`/`.env.*`/`.DS_Store`/`__pycache__`/`node_modules`/`.git` and any symlink.
* A reserved (never-written-to) `hermes_profile/` archive path, documented in the manifest, for a future *supported* Hermes profile export once Hermes is integrated (Phase 3+). Nothing is fabricated there in the meantime.

All archive paths are relative, forward-slash-separated, and contain no absolute home-directory path. The archive is written to a temp file inside `exports/` and only `os.replace()`d into its final name once fully written — an interrupted export can never appear as a finished one. A `flock`-based lock file prevents two exports running concurrently. Before writing anything, the source database is checked with `PRAGMA foreign_key_check` and `PRAGMA integrity_check`; a corrupt or unreadable database aborts the export with no partial file left behind.

### 5.2 Import validation (`backend/app/import_service.py`)

An untrusted archive is **never** extracted into `JARVIS_DATA_DIR` directly. `validate_archive()` always extracts into a fresh `tempfile.mkdtemp()` directory first, and only that copy is inspected. Checks, in order: ZIP structural sanity (member count and total uncompressed size caps, no absolute paths, no `..` traversal, no symlink/special-file members, no duplicate members) *before* extraction; then, after extraction, manifest schema validity and a supported `export_format_version`; SHA-256 checksum verification of every declared file; rejection of any extracted file not declared in the manifest; and finally opening the archived database read-only to run `integrity_check`, `foreign_key_check`, confirm its Alembic revision is one this codebase actually knows about (via `alembic.script.ScriptDirectory`, not just "equals current head" — an older *known* revision is fine, an unrecognised one is rejected as unsupported/future), and confirm all six expected domain slugs are present.

### 5.3 Restore (`backend/app/import_service.py::restore_archive`, CLI-only)

Restoration is deliberately **not** exposed over HTTP — it can replace a live database, so `jarvis-cli restore` is the only supported path in this phase (see `README.md` for exact commands). It always calls `validate_archive()` first and aborts untouched on any failure. If the target directory already has a database, it refuses unless `--confirm` is passed, and — before touching anything — copies the existing `database/documents/domain-summaries/skills/configuration` into a sibling `*.rollback-<timestamp>/` directory, verified with its own integrity check. The archived database is copied into place, `alembic upgrade head` is run against it (supporting restore-then-migrate from an older known schema), and a post-migration integrity check plus a six-domain check runs before success is reported. Any exception during this sequence restores the target from the rollback copy and re-raises, so a failed restore leaves the previous installation exactly as it was. The rollback copy is never auto-deleted, even on success — its path is reported so Bernardo can clean it up once satisfied.

### 5.4 Backups (`backend/app/backup_service.py`)

Backups use the same SQLite online-backup snapshot mechanism as export, written atomically (temp file + `os.replace`) with a `.sha256` sidecar, into `backups/{daily,weekly,monthly}/jarvis-backup-<category>-<timestamp>.sqlite`. Retention targets are 7 daily / 4 weekly / 12 monthly; pruning only ever deletes files matching the exact `jarvis-backup-<category>-<timestamp>.sqlite` pattern inside that category's own directory, never follows symlinks, and never touches an unrecognised file. A snapshot that fails its own post-backup integrity check is deleted immediately and never left behind as if successful.

There is no recurring scheduler in this phase — see §5.5.

### 5.5 Startup due-check, not a scheduler

`run_due_backups()` runs once during FastAPI's lifespan startup and creates a backup for any category whose most recent backup is older than that category's interval (24h/7d/30d) or missing entirely. This is a deliberately lightweight substitute for real recurring scheduling, which is deferred until a real need is demonstrated (see `docs/DECISIONS.md`). A due-backup failure is logged and never blocks startup.

### 5.6 API surface vs. CLI

`POST /api/export`, `GET /api/exports`, `GET /api/exports/{filename}/download` (filename constrained to the exact export-naming regex and confined to `exports/`, defeating path traversal), `POST /api/backups`, `GET /api/backups/latest`, and `POST /api/imports/validate` (validates an uploaded archive and reports pass/fail — never restores) are exposed over HTTP. Restoration is CLI-only (`jarvis-cli restore`); see `README.md` for exact commands.

## 6. Memory Architecture (implemented, Phase 4)

### 6.1 Schema (migration `0003_memory_and_context`)

* **`memory_items`** — the stable logical memory: scope (`global`/`domain`, enforced by a CHECK constraint requiring exactly one of "domain scope + a domain_id" or "global scope + no domain_id"), kind, title, status (`active`/`archived`/`deleted`), importance (1-5), confidence (0-1), sensitivity (`normal`/`sensitive`), optional event/valid-from/valid-until dates, optional source message/conversation/note, `current_version_id`, and `supersedes_id`/`superseded_by_id` links.
* **`memory_versions`** — every content change creates a new row here; nothing is ever updated in place. Carries its own title/kind/content/importance/confidence/sensitivity/event_date snapshot, a `change_reason`, a `source` tag (`explicit_remember`/`edit`/`supersede`), and a `(memory_item_id, version_number)` uniqueness constraint that defends against a duplicate/concurrent-update race producing two "version 2"s.
* **`domain_summaries`** / **`domain_summary_versions`** — one current-summary slot per domain, same immutable-version pattern. Never auto-regenerated; only `PUT`/`DELETE /api/domains/{slug}/summary` touch it.
* **`structured_records`** — domain-scoped, `record_type`-tagged, Pydantic-validated JSON payload (`app/structured_records.py`); never accepts arbitrary unbounded JSON. See §6.4.
* **`context_snapshots`** — one row per `agent_run` that reached context construction (see §6.3), FK'd 1:1 to `agent_runs.id`.
* **`memory_fts`** — a derived, rebuildable SQLite FTS5 virtual table (title + content, with scope/domain_id as unindexed filter columns). Never authoritative; see §6.2.

Editing (`POST /api/memories/{id}/edit`) creates version N+1 on the *same* memory item. Superseding (`POST /api/memories/{id}/supersede`) creates a **new** memory item, archives the old one, and links both directions (`supersedes_id`/`superseded_by_id`) — used when a memory isn't just updated but genuinely replaced by a different one. Archiving removes a memory from retrieval without touching its history. Permanent deletion (`POST /api/memories/{id}/delete`) requires the caller to submit the memory's *exact current title* as confirmation, creates a verified rollback backup first (`backups/pre_delete/`, via the same consistent-snapshot mechanism as Phase 2's daily/weekly/monthly backups), and only then hard-deletes the item and all its versions (cascading FKs), detaching (not cascading into) anything that referenced it via `supersedes_id`/`superseded_by_id`.

### 6.2 Why FTS5, not embeddings

Phase 4 deliberately uses SQLite's built-in FTS5 lexical search instead of embeddings: it needs no external API call (keeping memory fully local and model-independent), no vector index to keep in sync, and no additional dependency — and it's good enough for a personal-scale memory store where exact/near-exact term matches dominate real queries. `memory_fts` is populated on every memory write (`app/fts_service.py::upsert_memory_fts`) and can be fully rebuilt from `memory_items`/`memory_versions` at any time (`rebuild_fts`, exposed as `POST /api/memory-index/rebuild`) — after a restore, or if ever suspected out of sync. The original memory content is always authoritative; the index is derived. A future phase may add embeddings as an *additional* retrieval signal without removing this one.

A natural-language query is tokenized and every token is wrapped as a quoted literal phrase joined with `OR` (`sanitize_fts_query`) — this defends against FTS5 syntax errors from punctuation/operators/unusual Unicode in arbitrary user text, and (deliberately, discovered during live testing — see `docs/DECISIONS.md`) avoids FTS5's default *AND*-between-terms behavior, which would otherwise require every word of a whole question (including "what"/"do"/"you") to appear in a single short memory to match at all. When lexical search yields nothing, retrieval falls back to a deterministic importance-then-recency ordering — never silently empty context.

### 6.3 Context construction (`app/context_builder.py`)

For each turn, the bounded context package is assembled in a fixed, clearly delimited order:

1. Minimal Jarvis system/safety instruction (identity, uncertainty, no medical diagnosis, no completed-action claims, and the prompt-injection boundary below).
2. Compact active global profile (top active global memories by importance/recency, within a budget).
3. Active-domain name and description.
4. Current active-domain summary (its current version only).
5. Relevant active-domain memories (FTS5 lexical match against the turn's text, falling back to importance/recency).
6. Relevant structured records for the active domain (most recent, bounded).
7. Explicitly requested secondary-domain context — only ever present when the turn's `additional_domain_ids` names it, clearly labeled `Additional context — {DOMAIN} (explicitly included for this turn only)`. Never included because it seems semantically related.
8. Recent messages from the current conversation (bounded by `hermes_max_context_messages`).
9. The current user message (naturally the last of the bounded recent messages, since it was already saved before context is built).

**General conversations** (`domain: Domain | None`, Phase 6, D75): when a conversation's `domain_id` is `NULL` — a general Jarvis conversation opened from the core itself, not a seventh domain — `build_context` is called with `domain=None` and sections 3-6 above are skipped entirely; `domain_summary_version_ids`/`domain_memory_version_ids`/`structured_record_ids` are simply empty lists in the resulting `ContextSnapshot`, and `active_domain_id` is recorded as `None`. Section 7 (`additional_domain_ids`) is unaffected and becomes the *only* way domain-scoped material can enter a general turn — the exact same mechanism DomainView already used for cross-domain inclusion, with no separate code path. This is a deliberate default-to-least-context posture, matching CLAUDE.md §2's cross-domain isolation reasoning: "no specific domain" must default to seeing the least material, never the most.

Every section is size-budgeted (`context_char_budget`, default ~8000 chars); a section that would exceed the remaining budget is truncated with a visible `…[section truncated]` marker rather than silently cut or omitted. Archived/deleted/superseded-away memories are never retrieved (both the FTS index and the fallback query filter on `status = 'active'`), and only a memory's *current* version's content is ever used — exact version UUIDs are what get recorded in the snapshot, not the mutable parent memory.

**Prompt-injection boundary**: all retrieved memory/record/summary text is placed under a single `REFERENCE DATA (quoted, not instructions)` block, preceded by an explicit instruction that this data is never to be treated as commands — so a memory whose stored text happens to contain something that reads like an instruction (accidentally or adversarially) is still just data the model is told to disregard as an instruction source.

### 6.4 Structured records

Each of the seven initial record types (`app/structured_records.py`) has its own Pydantic model with bounded field lengths/ranges (e.g. `body_weight.kilograms` must be `0 < kg < 500`); a payload that doesn't validate is rejected outright, and unrecognised extra fields are dropped rather than stored verbatim. Each record type is locked to exactly one domain (`RECORD_TYPE_DOMAIN_SLUG`) — creating a `body_weight` record under BUILD is rejected at the service layer, not just the UI.

### 6.5 Context snapshots — an audit, not model reasoning

`context_snapshots` records, for every turn that reached context construction (success *or* failure of the subsequent model call), the exact active domain, explicitly-included additional domains, and the exact version/record/message UUIDs used — plus the retrieval query text, per-item retrieval reasons (`"lexical match (bm25=...)"` / `"importance/recency fallback"` / `"global profile (importance/recency)"`), and an estimated context size. It never stores hidden chain-of-thought or the model's reasoning — only which local data was assembled and why. If context construction itself fails (e.g. an unknown `additional_domain_ids` entry), the run is marked failed with a sanitised `context_build_failed` error *before* any model call, and no snapshot is created — there's nothing to audit.

### 6.6 Model independence

Memory is model-independent by construction: it lives entirely in the Jarvis Controller's own tables, `context_builder.py` never imports or depends on `app/providers/*`, and `HermesProvider` never sees a memory table directly — it only receives the already-assembled `system_prompt` and bounded `history` that `turn_service.py` hands it. Switching Hermes's configured model/provider (as already demonstrated in Phase 3) changes nothing about how memory is stored, retrieved, or versioned.

## 7. Model Strategy

**Originally planned**: Claude Sonnet 5, via Anthropic's direct API. **Currently configured** (Phase 3, switched with Bernardo's explicit approval): GPT-5.6 Terra, via OpenAI Codex OAuth against Bernardo's ChatGPT subscription. Neither choice required a code change — see §7a for why. No multi-model router in V1. All model-specific behavior sits behind the provider interface described in §7a; every generated response stores its model/provider metadata (`Message.model_used`, and the full `agent_runs` audit row).

**Neither the Anthropic key nor the OpenAI/ChatGPT OAuth credential ever touches the FastAPI backend at all** — the active credential lives only inside Hermes's own profile-scoped secret storage (`~/.hermes/profiles/jarvis/.env` for an API-key-based provider, or `~/.hermes/profiles/jarvis/auth.json` for the current OAuth-based one), established directly by Bernardo via `jarvis setup model`. This is a stronger guarantee than "backend secret configuration excluded from exports": the backend's process, code, and `backend/.env` never see this credential in any form, regardless of which provider it is. See §8 for the separate, backend-owned secret (the Hermes API bearer token) that this must not be confused with.

### 7a. Agent-provider interface (implemented, Phase 3) — genuinely model-independent, not just in intent

`backend/app/providers/base.py` defines a small `AgentProvider` protocol: `health(timeout)`, `model_info(timeout)`, and `send_turn(system_prompt, messages, timeout)` returning a `TurnResult` (content, model, provider name, latency, token usage, external run id) or raising a `ProviderError` with a sanitised `code` (`unavailable`/`timeout`/`auth_failed`/`malformed_response`/`rate_limited`/`unknown`) and human-readable summary — never a raw exception or provider-internal string that could carry a secret.

`backend/app/providers/hermes.py` is the first (and currently only) implementation, calling the local Hermes API server's OpenAI-compatible endpoints:

* `GET /health` — unauthenticated liveness check → `hermes_available` in `GET /api/agent/status`.
* `GET /v1/models` (authenticated) — confirms the bearer token is valid and a model is configured → `model_configured`.
* `POST /v1/chat/completions` (authenticated) — the actual conversational turn. **Critically, this request never includes a `model` field.** Hermes's API server only recognises its own virtual per-profile alias (e.g. `"jarvis"`) as a `model` value; anything else is treated as a per-request override attempt that fails unless it matches a configured route. Omitting the field entirely lets the `jarvis` profile's own configured provider/model — whatever it currently is — fully own that decision. `Settings.hermes_model` is a human-readable label only (used for `Message.model_used` / `agent_runs.model` / the HUD), updated by an operator when the underlying Hermes config changes; the backend code itself never reads or depends on what that label says. Changing models is purely a `jarvis config set model ...` / `jarvis setup model` action — zero Jarvis code or config changes required.

Because everything downstream of `turn_service.py` only depends on the `AgentProvider` protocol, a different provider could be substituted (or a mocked/fake one used in every automated test — see `tests/conftest.py::FakeProvider`) without touching the database, the turn endpoint, or the frontend.

### 7b. Request flow for one turn

```
Frontend "Send to Jarvis"
  → POST /api/conversations/{id}/turns  (idempotency_key, content)
  → turn_service.send_turn():
      1. idempotency check (existing agent_runs row for this key? return it, don't call Hermes again)
      2. save the user Message
      3. create an agent_runs row (status=running)
      4. build a bounded context: global instruction + active domain name/description
         + conversation title + last N messages (hermes_max_context_messages) + the new message
      5. HermesProvider.send_turn(...) → Hermes API server (bearer-token authenticated, no model field sent)
         → Hermes's own agent loop → whichever provider/model the profile is configured for
           (currently OpenAI Codex OAuth / GPT-5.6 Terra — Hermes's own credential, never seen by FastAPI)
      6. on success: save the assistant Message (model_used set), mark the run succeeded,
         record latency/tokens/external_run_id
      7. on ProviderError: mark the run failed with the sanitised code/summary; the user
         message is still preserved; no assistant message is invented
  ← TurnRead (run id, status, both messages, provider/model, usage, sanitised error if any)
```

No semantic memory search or cross-domain retrieval happens in this phase — the "bounded, basic context" above is the entire prompt construction.

## 8. Hermes Integration (implemented, Phase 3)

One dedicated Jarvis Hermes profile named `jarvis` (not the default profile, not six). Created blank (`hermes profile create jarvis --no-skills`), with its own isolated `.env`/`config.yaml`/`SOUL.md` — no cloned memories or credentials from any other profile.

**Effective, live-verified configuration** (via the gateway's own `/v1/toolsets` introspection endpoint, not just the config file — see `docs/DECISIONS.md`):

* Only the `skills` and `memory` toolsets are enabled for the `api_server` platform; every other built-in toolset (web, browser, terminal, file, code_execution, vision, video, image_gen, video_gen, x_search, tts, stt, todo, context_engine, session_search, clarify, delegation, cronjob, homeassistant, spotify, discord(_admin), yuanbao, computer_use, a2a) is disabled.
* `memory.write_approval` and `skills.write_approval` are both `true` — nothing is written without approval.
* `curator.enabled` is `false` (no background autonomous skill maintenance).
* `gateway.api_server.max_concurrent_runs` is `1`.
* No external memory provider is configured (`memory.provider` empty; no `~/.honcho/config.json` present).
* No messaging gateway (Telegram/Discord/etc.), no cron jobs, no delegation/sub-agents.

Hermes's local API server (`gateway/platforms/api_server.py` in the Hermes Agent codebase — a different thing from Hermes's "messaging gateway" concept, which is unused here) binds `127.0.0.1:8642` only, requires a bearer token (`API_SERVER_KEY`, a 32-byte random hex value generated once and stored in the profile's permission-600 `.env`), and has CORS disabled — the browser calls FastAPI, never Hermes directly.

Jarvis's local database remains the authoritative personal-memory system regardless of what Hermes offers; Hermes's own memory/skills tools stay approval-gated and are not treated as Jarvis's memory store in this phase.

## 8a. Voice Integration (implemented, Phase 5)

Push-to-talk only — no continuous listening, matching CLAUDE.md §8. Two new endpoints, both stateless and unauthenticated (loopback-only, same as the rest of the API):

* `POST /api/voice/transcribe` — multipart audio upload → `{"transcript": "..."}`, via local `faster-whisper` (`app/voice/faster_whisper_stt.py`).
* `POST /api/voice/speak` — `{"text": "..."}` → `audio/mpeg` bytes, via Microsoft Edge TTS (`app/voice/edge_tts_tts.py`, free endpoint, sanctioned as the initial TTS choice).

Both providers sit behind `SpeechToText`/`TextToSpeech` Protocols (`app/voice/base.py`), injected onto `app.state` in `main.py` and resolved via `deps.get_stt`/`deps.get_tts` — the same provider-independence shape as `AgentProvider` (§7a). See `docs/DECISIONS.md` D36.

**Raw audio handling**: the uploaded recording is written to an OS temp file (`tempfile.mkstemp`, never under `JARVIS_DATA_DIR`) and deleted in a `finally` block regardless of whether transcription succeeds — CLAUDE.md §8's "do not retain raw recordings by default" (D37). Only the transcript string is ever persisted (as an ordinary user `Message`, once sent through the existing turn flow).

**Frontend** (`frontend/src/hooks/usePushToTalk.ts`, wired into `DomainView.tsx`): hold Space (while no text field is focused) or hold the on-screen "Hold to talk" button → `MediaRecorder` records → release → `POST /api/voice/transcribe` → the transcript is sent through the existing `sendTurn` flow exactly as if typed → the assistant's reply is sent to `POST /api/voice/speak` and played back. Escape cancels an in-progress recording. Voice states shown to the user (`idle`/`listening`/`transcribing`/`thinking`/`speaking`/`error`) map onto CLAUDE.md §8's state list, with "routing"/"retrieving context" collapsed into "thinking" since the turn endpoint doesn't expose those sub-stages separately. This phase adds only these functional controls to the existing plain HUD — no visual redesign (see `docs/DESIGN_DIRECTION.md`, D35).

A live (not mocked) bug was found and fixed in this phase: see `docs/DECISIONS.md` D38 — the push-to-talk button must stay enabled for the entire "listening" phase, including while a `getUserMedia` permission prompt is still unresolved, or a mouse/touch release has no way to reach a disabled button's handlers.

**8a-i. Transcription latency: one real fix kept, one attempted fix reverted after a severe incident (D107)** — a diagnostic pass on the installed app, not a model/provider change. `FasterWhisperSTT` (`app/voice/faster_whisper_stt.py`) still uses `model_size="base"`, `device="cpu"`, `compute_type="int8"` and default decoding settings, benchmarked on the target M2 Pro at ~0.6-1.0s warm per short push-to-talk clip — already reasonable, left unchanged.

* **Kept: the transcription endpoint no longer blocks the event loop.** `POST /api/voice/transcribe` (`app/routers/voice.py`) is an `async def` handler that was calling `stt.transcribe()` — synchronous, CPU-bound work — directly, stalling the entire event loop (including the Phase 10 scheduler runtime's background task and any other concurrent request) for the full ~0.6-1.0s of inference. Fixed by offloading to a worker thread: `await asyncio.to_thread(stt.transcribe, path)`. Changes nothing about wall-clock transcription time; only stops it from blocking unrelated work.
* **Attempted, then fully reverted: eager model preload at startup.** A `FasterWhisperSTT.preload()` method, called from `app/main.py`'s lifespan to force `WhisperModel(...)` construction (~0.9s) during startup instead of on the first real push-to-talk turn, was deployed to the real installed app and caused a severe, reproducible incident: constructing the model *during the app's own startup lifespan* (before the server begins listening) triggered a self-sustaining process-respawn loop — the whole frozen binary re-executed itself roughly once per second, indefinitely, each cycle re-running the full lifespan including the integration scheduler, which on the real Mac meant a fresh Google Calendar Keychain access attempt on every single cycle (the "infinite" Keychain-prompt incident this caused). An ordinary **lazy** transcription (construction happening well after the server is already listening) was confirmed safe — one bounded, harmless extra process, never a loop. `preload()`, its setting, and its lifespan wiring were all removed outright rather than merely disabled. The underlying packaging-level defect this surfaced (§22's onefile sidecar missing `multiprocessing.freeze_support()`) was root-caused and fixed separately — see D109 below; eager preload itself was not reintroduced. See `docs/DECISIONS.md` D107 for the full incident account and isolated reproduction evidence.

## 8b. macOS Launcher / Local Runtime (implemented, Phase 7)

**Static frontend serving** (D41/D42): `backend/app/main.py` mounts `frontend/dist` as static files at `/` whenever that directory exists (built via `npm run build`), registered after every `/api/...` router and after an explicit catch-all 404 for unmatched `/api/*` paths. This means ordinary use needs only **one** HTTP process/port (the FastAPI backend on `127.0.0.1:8000`) plus the independently-lifecycled Hermes gateway (`127.0.0.1:8642`) — no separate frontend dev server. `npm run dev` still works unchanged for frontend development.

**`scripts/jarvisctl.sh`** (D44) is the local runtime controller, with all state under `~/Library/Application Support/Jarvis` (D43) — never `JARVIS_DATA_DIR`:

```
open / focus   Idempotent start-or-focus: start the Hermes gateway if it
               isn't already running, apply Alembic migrations, build the
               frontend, start+health-check the backend (bounded polling,
               never a fixed sleep), then open/focus a dedicated app-mode
               Chrome window (falls back to the default browser). If the
               backend is already healthy, this just reopens the window —
               no rebuild, no restart, no duplicate process.
status         Reports Hermes gateway reachability, backend health + PID,
               and whether start-at-login is installed.
stop            Stops only the Jarvis-owned backend process, and only after
               verifying its PID actually is a `uvicorn app.main:app`
               process (never trusts a stale/reused PID blindly). Does not
               touch the Hermes gateway (separate lifecycle, as in Phases
               3-6 — see scripts/hermes-gateway.sh).
install-startup /
uninstall-startup
               Render/remove a LaunchAgent (see below) — never invoked
               against the real machine without Bernardo's explicit
               approval in-session first.
```

Port conflicts are detected two ways: a best-effort `lsof`-based pre-check, and — since that pre-check can't be guaranteed on every system/shell — a fallback that recognizes uvicorn's own "address already in use" failure and reports it as an actionable port conflict (with `lsof` details) rather than a raw traceback, never retrying with a killed/duplicated process.

**Start-at-login** uses a project-owned, placeholder-only template (`macos/com.bernardo.jarvis.launcher.plist.template`) — `install-startup` substitutes this machine's real paths and writes the result to `~/Library/LaunchAgents/`, never committing or exporting the rendered file. `RunAtLoad=true`, `KeepAlive=false` (a login launcher, not a process supervisor).

**The `Control+Option+J` global shortcut is deliberately never installed automatically** — CLAUDE.md's macOS safety boundary forbids silently modifying macOS Shortcuts, so binding it is always a one-time manual step Bernardo performs himself in Shortcuts.app (see README.md), pointing a single "Run Shell Script" action at `scripts/jarvisctl.sh open`.

**Testing**: `scripts/test_jarvisctl.sh` runs the full behavior above against a fully isolated fake `JARVIS_HOME`/`JARVIS_DATA_DIR`/port — cold start, idempotent repeat, data survival across stop/restart, stale-PID-file safety, and LaunchAgent install/uninstall (validated with `plutil -lint`) — without ever touching the real machine.

## 9. Permission Tiers and the Action Lifecycle (implemented, Phase 8)

| Tier | Behavior | Examples |
|---|---|---|
| Read | Executes without confirmation, when scoped | read permitted files, structured records, approved sources, calendar (post-integration) |
| Draft | Produces proposed output, does not transmit/commit | draft email, propose calendar change, prepare message |
| Confirm | Requires explicit approval immediately before execution | `memory.create`, `structured_record.create`, `domain_summary.update` (the three capabilities implemented so far — see below), and later: send email, change calendar, modify external systems |
| Prohibited | Not permitted by default | destructive file ops, purchases, financial transactions, public posting, cross-domain sensitive-data exposure, exposing local services publicly |

Every consequential tool action generates an audit record. Phase 8 implements this concretely as a **default-deny capability registry plus an auditable action lifecycle** — direct actions a user takes through existing UI controls (saving a note, editing a memory by hand) are unaffected and never touch this system; it exists specifically for mutations *Jarvis itself* proposes.

**Capability registry** (`app/capabilities.py`, D46): a fixed, code-owned dict — `memory.create`, `structured_record.create`, `domain_summary.update`, all "Confirm" tier, all controller-owned internal records with no external side effect. Not a database table; not extensible at runtime by anything (a skill, an import, a future model). The `action_proposals.capability_id` column's own `CHECK` constraint enumerates exactly these three strings, so an unknown capability cannot even be inserted at the database layer.

**Action lifecycle** (`app/action_service.py`, D47): `proposed → approved → executing → succeeded|failed`, or `→ denied`/`→ expired` at any point before execution:

```
POST /api/actions                       propose (capability_id, domain_id, arguments, reason)
POST /api/actions/{id}/approve          requires the exact payload_digest; mints a single-use,
                                         5-minute confirmation_token
POST /api/actions/{id}/execute          requires that exact confirmation_token
POST /api/actions/{id}/deny
GET  /api/actions[?status=][?domain_id=]
GET  /api/actions/{id}                  proposal + full ActionAuditEvent history
```

`payload_digest` is a SHA-256 of `{capability_id, domain_id, arguments}`, computed once at proposal time and never recomputed — approval is bound to that exact content, not just an ID. The confirmation token is single-use (consumed on the execute *attempt*, not on success, so a failing handler can't be retried indefinitely with a leaked token) and scoped to exactly one proposal (a token approved for proposal A never validates against proposal B's execute call, even if both are otherwise valid — the "cross-domain confirmation" rejection). Every transition writes an immutable `ActionAuditEvent` row. Model-generated text is never treated as authorization — there is no code path from a Hermes response's content to `approve_action`/`execute_action` at all (D47; see `test_action_prompt_injection.py`).

## 9a. Lifecycle Hooks (implemented, Phase 8)

`app/hooks.py` (D49) is a small in-process registry — `register_hook(phase, name, fn)` — with four phases and an explicit, ordered registration (this exact order, read top-to-bottom in the file):

* **before_context**: `validate_domain_exists` — guards `turn_service.send_turn` against a stale/deleted `domain_id` ever reaching context construction.
* **before_action**: `capability_allowlist` → `confirmation_validity` → `recursion_guard` — re-verifies the capability is still allowlisted, *is* the enforcement point for the payload-digest/token/expiry contract above, then refuses to re-execute an already-executing/succeeded/failed proposal.
* **after_action**: `audit_after_action` — records a successful completion.
* **on_failure**: `audit_on_failure` — records the failure detail; the proposal's own status is already set to `failed` (with any partial DB state rolled back) before this runs.

Every hook invocation — allowed or blocked — is written as an auditable `HookEvent` row before its result is used, via `hooks.run_hooks(phase, context)`. A hook returning `allowed=False` (or raising, treated the same) stops that phase immediately — fail closed, before the risky operation proceeds. Hooks are plain Python functions in this codebase; none execute arbitrary user-provided shell commands or code, none silently rewrite stored messages/memories, and none depend on which reasoning model/provider is configured. `hooks.registered_hook_names(phase)` is the source of truth for ordering (pinned by `test_hooks.py`).

This is a subset of the original five-hook sketch (`pre_turn`/`post_turn`/`pre_tool_call`/`post_tool_call`/`session_end`) — Phase 8 implements the four phases CLAUDE.md §13 lists as the minimum (before context construction, before/after/on-failure of action execution). `post_turn` memory-promotion hooks and a `session_end` summary hook remain unimplemented; add them only when a concrete need is demonstrated, following this same registry pattern.

## 9b. Skills (implemented, Phase 8)

A skill (`app/skill_service.py`, D48) is a named, versioned, declarative workflow — never arbitrary executable code. Schema: `Skill` (mutable convenience fields mirroring the current version: `slug`, `name`, `description`, optional `domain_id`, `invocation_phrases`, `status` ∈ `draft|active|archived`, `created_by` ∈ `user|jarvis`) + immutable `SkillVersion` history (`workflow_steps`: a list of `{capability_id, description}`, each `capability_id` validated against the same fixed registry as above).

```
POST /api/skills                    create (always starts as draft)
GET  /api/skills[?status=][?domain_id=]
GET  /api/skills/{id}               current version + full version history
POST /api/skills/{id}/edit          new immutable version — always demotes back to draft
POST /api/skills/{id}/activate      re-validates workflow steps against the capability registry first
POST /api/skills/{id}/archive
POST /api/skills/{id}/invoke        creates one ActionProposal per workflow step — nothing more
```

Invoking a skill never mutates anything directly — it only calls `action_service.propose_action` once per workflow step, so invocation always passes through the exact same approve/execute lifecycle as a manually-created proposal. A domain-scoped skill's `domain_id` is forced onto every proposal it creates (never taken from the invocation's own arguments), so a domain-scoped skill structurally cannot retrieve or write an unrelated domain. Editing a skill — active or not — always sets its status back to `draft`, requiring the same explicit re-activation review a new skill needs; only `active` skills can be invoked. Four clearly-labeled example templates (`example-body-weekly-checkin`, `example-build-project-checkpoint`, `example-path-deadline-review`, `example-life-daily-planning`) are seeded at startup as `draft`, `created_by="jarvis"` — never auto-activated.

Skills, their versions, and completed action audit history are ordinary rows in the same SQLite database as everything else — no export/import changes were needed (Phase 2's `create_export` already snapshots the whole database file). A dedicated post-restore safety measure (`import_service._expire_stale_action_proposals`, D50) forces any non-terminal `action_proposals` row (`proposed`/`approved`/`executing`) to `expired` immediately after every restore, so a pending or already-approved mutation from one installation can never become executable merely by being restored into another.

## 9c. Integrations: Google Calendar, Google Health, Local Documents (Phase 9 — complete, live acceptance passed, D67)

Three model-independent, controller-owned integrations, each following the same provider-interface shape as §7a's `AgentProvider` and §8a's `SpeechToText`/`TextToSpeech`: connection status, OAuth connect/disconnect, manual sync, normalized local caching, health/errors, token refresh, revocation, and context retrieval.

**Correction (D59-D61)**: the original Phase 9 implementation told Bernardo to create a Google "Desktop app" OAuth client while relying on incremental authorization — which Google documents as unsupported for installed/Desktop clients — and built the health-data provider against the legacy Fitbit Web API, which Google is retiring in September 2026. Both Google Calendar and the health-data integration now use a Google OAuth **Web application** client (the backend performs the code exchange itself and owns a fixed callback per provider — exactly what a Web application client type is for), and the health-data provider now targets the current Google Health API instead of `api.fitbit.com`. See D59-D61 for the full rationale.

**Credentials** (`app/credential_store.py`, D53): OAuth client id/secret, access tokens, refresh tokens, and token-expiry metadata live *only* in the macOS Keychain via a `CredentialStore` protocol — never in SQLite, `.env`, source, frontend state, logs, exports, or backups. `KeychainCredentialStore` wraps the `keyring` package for reads and deletes, but writes go through `app/keychain_update.py`'s in-place `SecItemUpdate` first (falling back to `keyring.set_password()`'s delete-and-recreate only for a genuinely new item) — see D108: `keyring`'s own write path always deletes and recreates the item, resetting its Access Control list on every write, which is what caused a Keychain permission prompt to recur after every OAuth token refresh even when correctly configured. `FakeCredentialStore` (in-memory) is the only implementation automated tests ever use. `jarvis-cli configure-integration <provider>` is the one-time local entry point (interactive prompts, hidden secret input) — never through a Jarvis API endpoint, never pasted into a chat session.

**OAuth flow** (`app/oauth_flow.py`, D54): Authorization Code + PKCE (S256) against a Google **Web application** client, loopback-only redirect (`http://127.0.0.1:8000/api/integrations/{provider}/oauth/callback` — this same FastAPI backend, not a separately-bound listener), cryptographically random `state`, single-use consumption (deleted from the in-memory `OAuthFlowStore` the instant it's read, so a replayed callback always fails), a 10-minute bounded lifetime, and exact provider-match validation. State/PKCE verifiers are held only in memory (never in SQLite) — a mid-flow backend restart just fails that one attempt cleanly, which is correct: there is nothing to leak or restore.

**OAuth credential persistence and scope filtering** (`integration_service.py`, D65): Google associates OAuth consent with the (user, Cloud project) pair, not (user, client_id) — confirmed live, a callback for one integration's client can carry the other integration's scopes when both share a project. `_normalize_granted_scopes()` filters every callback's returned scope string down to only the scopes that specific provider's own code ever uses, falling back to the previously-stored scopes if filtering leaves nothing (never overwriting a real grant with an empty one). `_persist_oauth_connection()` is the shared, safe completion path for both providers' callbacks: Keychain is written first, and a Keychain failure raises before the database row is ever marked connected — DB and Keychain can never disagree with each other, and a missing optional `refresh_token` in an incremental response never deletes a previously-stored one (`_store_tokens` only ever writes a field it actually received).

**Google Calendar** (`app/providers/google_calendar.py`): least-privilege incremental scopes — `calendar.calendarlist.readonly` + `calendar.events.readonly` by default; `calendar.events.owned` (write access to *owned* calendars only, never the broader `calendar.events`) requested only via a fresh, explicit incremental-consent round trip (`include_granted_scopes=true`) when Bernardo turns on write access. Normalized local cache: `CalendarCalendar` (which calendars are known/selected) and `CalendarEventCache` (per-event, with `etag`/source-updated timestamp), refreshed only by explicit manual sync (`POST /api/integrations/google_calendar/sync`) over a bounded date range (1 day past, 30 days future). The write capability never assumes a requested scope was granted: `capabilities.py`'s `validate_domain_for_capability` checks `integration_service.has_scope(...)` for `calendar.events.owned` at propose time, and `calendar_capability.py`'s `_require_write_scope_granted` re-checks the same thing immediately before execution — a connection whose scope narrows or disconnects between propose and execute is refused cleanly rather than silently permitted.

**Google Health** (`app/providers/google_health.py`, D60-D61, breadth-corrected D64) — internal provider id `google_health`, labeled plainly "Google Health" in the UI (not Fitbit-specific — it reads reconciled, consented data that can originate from Fitbit, Pixel Watch, Health Connect, Google Fit, or any other source connected to the account; the UI says so and never claims a specific source or complete metric coverage). Read-only, `googlehealth.activity_and_fitness.readonly` / `googlehealth.health_metrics_and_measurements.readonly` / `googlehealth.sleep.readonly` scopes only (never location/nutrition/write, never `include_granted_scopes` — D63).

Built around an explicit, typed metric registry (`ROLLUP_METRICS`, `DAILY_LIST_METRICS`, `SESSION_METRICS`) rather than a single daily-summary shape — each entry records the Google Health data-type id, governing scope, REST operation, sync category, and BODY-only eligibility. Three fetch mechanisms, per official operation support, verified live (D64):

* `dailyRollUp` — interval-summable metrics (steps, distance, floors, active zone minutes, active/total calories, heart rate). Reconciled by default (deduped across phone/watch). Range limits enforced client-side: 14 days for heart-rate/total-calories, 90 days otherwise — a request wider than a metric's limit is transparently split into consecutive, non-overlapping chunks by `_chunk_date_range()`/`_daily_roll_up_chunked()` (D65) rather than failing outright; a chunk failure is recorded against that metric without discarding data already fetched from other chunks of the same call.
* Unfiltered `list` + client-side date truncation — "daily-*" precomputed singleton types (resting heart rate, HRV, oxygen saturation, respiratory rate, VO2 max) and point samples (weight, body fat, blood glucose). The server-side `filter` parameter was live-verified to reject every field-name variant tried for these types; a bounded no-filter fetch truncated to the sync window is the safe fallback.
* Filtered `list` — sessions (sleep, exercise), each with its own live-verified filter convention (`sleep.interval.end_time` in UTC vs. `exercise.interval.civil_start_time` in civil time — not interchangeable). Sleep sessions carry full stage detail (`google_health_sessions.stages_json`); exercise sessions carry type/duration/calories/distance/heart rate. Both are keyed by Google Health's own stable resource name for idempotent upsert.

A metric's fetch failure is caught per-metric and recorded in a sync's `partial_failures`, never aborting the rest of the sync — `IntegrationConnection.last_sync_status` can be `"partial"` with a summary of which metrics failed, confirmed live (a 31-day sync correctly marked the 14-day-limited metrics as failed while ~15 others and both session types succeeded in the same call). Several numeric fields are JSON-encoded as strings (`type: string, format: int64` in the discovery doc — `steps.countSum`, `distance.millimetersSum`, etc.) and are cast defensively regardless of whether the API sends a string or number.

Daily Readiness Score, Sleep Score, Stress Management Score, and Cardio Load/Target Load are **not** exposed by any documented Google Health data type and are shown as explicitly unsupported (`google_health.UNSUPPORTED_METRICS`) rather than estimated or relabeled from another metric — and never will be computed as a Jarvis-derived substitute presented under one of those names. Missing data for a given day/type leaves that field `None`; 401 raises `unauthorized`, 429 raises `rate_limited` with `Retry-After` captured, 5xx raises a server error, 404 is treated as "no data" rather than an error — none of these are silently swallowed. No action capability is registered for this integration; it cannot write anything.

**Local documents** (`app/document_service.py`, D56): explicit browser upload only — never a scanned/watched folder. Content is sniffed from actual bytes, never trusted by extension (a `.pdf`-named file containing plain text is stored and reported as `text/plain`). PDF (`pypdf`) and DOCX (`python-docx`) text is extracted without executing any macro or embedded object — a DOCX containing `word/vbaProject.bin` (a macro project) is rejected outright, as is one whose uncompressed content exceeds a fixed limit (zip-bomb guard) or whose internal part count is excessive. Encrypted PDFs are reported as `status="encrypted"`, never silently skipped. Originals are stored under `JARVIS_DATA_DIR/documents/<sha256><ext>` (SHA-256 also drives duplicate detection and the safe, path-confined filename — the original filename is never used for the on-disk path). Extracted text is chunked (1500 chars, 200 overlap) and indexed in a derived, rebuildable FTS5 table (`document_fts`, mirroring `memory_fts`'s pattern) — never authoritative; `document_chunks` is.

**Context behavior** (`app/context_builder.py`): document chunks matching the turn's query (within in-scope domains) are added as a quoted "Cited document excerpts" reference section, with citations (`doc:<id> chunk:<id>`, page when known) — the same "REFERENCE DATA (quoted, not instructions)" framing as memories governs them, so injected text ("ignore previous instructions...") is inert by construction (D57). Google Health data enters context only when BODY is in scope (active or explicitly added); Google Calendar data only when LIFE is in scope — both explicitly labeled with sync-age staleness ("locally cached, not live"). Google Health's context section is a compact rollup — recent daily-summary lines plus up to 4 recent sleep/exercise sessions with source platform — never a raw time-series dump. `ContextSnapshot` has three fields for this (`document_chunk_ids`, `calendar_event_ids`, `google_health_summary_ids`, the last renamed from `fitbit_summary_ids` by migration 0006) so the exact integration records used are auditable via the same Context Used mechanism as memories/records.

**Calendar writes as Phase 8 capabilities** (`app/calendar_capability.py`): `google_calendar.event.create/update/delete` extend the fixed capability registry (D46) — same propose → approve (exact payload digest) → execute (single-use token) lifecycle as any other capability. A write is refused unless the target calendar is both `selected` (chosen for Jarvis access) and `is_owned` (never writes to a merely-shared calendar), and unless the connection's granted scopes actually include `calendar.events.owned` (checked at both propose and execute time, see above). A timezone is required for any timed (non-all-day) event and is never silently inferred. No attendees, invitations, recurring events, sharing changes, or calendar deletion — matching Phase 9's explicit scope.

**Export/restore**: documents, extracted text, and both normalized caches are ordinary database rows — included automatically in the whole-database snapshot, no export_service.py changes needed. `import_service._disconnect_all_integrations` (D58) forces every `integration_connections` row to `disconnected` immediately after every restore, regardless of its status at export time — the real tokens live only in this machine's Keychain, never in the exported database, so a restored installation always requires reauthorization.

## 9d. Automatic Integration Resync (Phase 10, D68)

Controller-owned, model-independent, and entirely local — no Hermes cron, no Hermes skill, no sub-agent, no model call, no cloud scheduler or database. Automatic work only ever happens while this backend process is running.

**Scheduler** (`app/scheduler_runtime.py::SchedulerRuntime`): a single `asyncio.Task` started/stopped by FastAPI's `lifespan` (`main.py`) — `start()` is idempotent (a second call is a no-op if already running, so there is structurally never a duplicate loop) and `stop()` cancels the task and awaits it, bounding shutdown. On start, it runs one synchronous startup catch-up pass, then begins a tick loop (`DEFAULT_TICK_INTERVAL_SECONDS = 30`) that checks both providers each pass. A plain sleep-loop was chosen over a heavier scheduling library deliberately (D68) — the requirement is small and fixed (two providers, tick-check-run), and none of a heavier library's extra features apply here.

**Logic layer** (`app/scheduler_service.py`, fully testable via an injected `clock` callable and fake providers — never `datetime.now()` called directly):

* `get_or_create_schedule`/`set_schedule` — per-provider configuration (`enabled`, `interval_minutes`), validated against a provider-specific allowed-cadence set (Calendar: 15/30/60 min; Google Health: 60/180/360/1440 min) enforced server-side, never only in the UI. Enabling sets `next_due_at = now` (one immediate sync); disabling clears it.
* `run_provider_sync` — the actual per-attempt orchestration, reusing `integration_service.sync_google_calendar`/`sync_google_health` (never duplicating provider logic). Guarded by a per-provider `threading.Lock` (`try_acquire_provider_lock`) so manual, scheduled, and startup-catchup syncs can never overlap for the same provider — a collision is recorded as a `"skipped"` run, and the manual-sync HTTP endpoint returns `409` in that case.
* `startup_catchup`/`tick` — both ask only "is this enabled provider's stored `next_due_at` in the past?" and run it *at most once* if so. `next_due_at` always advances from the real completion time of an attempt, never by replaying missed slots — this is what structurally prevents a catch-up storm after a long sleep/downtime, with no special-case "how overdue" logic needed at all.
* Failure handling: never crashes, never marks the real `IntegrationConnection` disconnected. Bounded exponential backoff (`interval × 2^failures`, capped at 8× the interval and an absolute 24 hours), honoring a provider's `Retry-After` when present (via `IntegrationError.retry_after`) by taking whichever wait is longer. `consecutive_failure_count` resets to 0 on the next success. A Google Health `"partial"` sync (some metric groups failed) is treated as success for scheduling purposes — the existing Phase 9 truthful-partial behavior is unchanged.
* Auditability: every attempt is recorded in `integration_sync_runs` (provider, trigger — `manual`/`scheduled`/`startup_catchup`, timing, outcome, a sanitized reason, non-sensitive result counts only — never a raw provider payload, event title, or credential). Bounded to the most recent 50 rows per provider (`_trim_history`, run on every insert).

**Schema** (migration `0009_integration_sync_schedules.py`, forward-only, 0001-0008 untouched): `integration_sync_schedules` (one row per provider, seeded `enabled=0`) and `integration_sync_runs`.

**Restore behavior**: `import_service._disable_all_integration_schedules` forces every schedule to `enabled=0, next_due_at=NULL` immediately after every restore, alongside `_disconnect_all_integrations` — a restored installation must never resume automatic sync against a provider that's simultaneously been forced disconnected in the same step.

**API/UI**: `GET`/`PUT /api/integrations/{provider}/schedule` and `GET /api/integrations/{provider}/sync-history` — an explicit local UI action, not a Phase 8 proposal (configuring Jarvis's own schedule metadata has no external side effect of its own). The Integrations Centre shows, per provider: an automatic-sync toggle, a constrained cadence selector, last successful sync, next scheduled sync, and a consecutive-failure/reconnect-required indicator when relevant — alongside the existing manual "Sync now" control, unchanged.

## 9e. Proactive Routines (Phase 10B, D70)

A fixed, controller-owned routine catalogue — never arbitrary cron — reusing §9d's exact scheduler loop rather than a second background task. No routine ever calls a model, mutates Calendar/Health data, writes a memory, sends a notification, speaks aloud, or contacts anyone; the only model-reachable action is the manual "Discuss with Jarvis" button.

**Catalogue** (`app/models_routines.py::ROUTINE_TYPES`): `morning_briefing`, `evening_checkin`, `weekly_review`. Each has one `RoutineSchedule` row (`enabled` defaults `False`, user-configurable local time/timezone, `weekday` only for `weekly_review`, `selected_domains_json`) and a bounded history of `RoutineRun` rows (`ROUTINE_RUN_RETENTION_PER_TYPE = 30`, trimmed via `_trim_history` on every insert — same `session.flush()`-before-trim pattern as §9d's `scheduler_service`, since this project's sessions are `autoflush=False`).

**Scheduler coexistence**: `scheduler_runtime.py`'s `_run_startup_catchup`/`_run_tick` call `routine_service.startup_catchup`/`tick` alongside `scheduler_service`'s equivalents in the same pass, each in its own try/except so a failure in one subsystem never blocks or crashes the other. There is exactly one `asyncio.Task`/one background loop for both.

**Timezone/DST-safe due-time computation** (`routine_service._next_occurrence_utc`): the candidate occurrence is constructed directly in the target IANA timezone's wall-clock terms (never by adding a fixed-offset `timedelta` to a UTC instant), then converted back to UTC — this is what correctly resolves Europe/Lisbon's DST transitions, verified against real October/November dates straddling the actual transition.

**Content assembly** (`build_morning_briefing`/`build_evening_checkin`/`build_weekly_review`): deterministic, source-referenced local summaries built from the existing Phase 4 `StructuredRecord` model (`life_task`, `path_deadline`, `build_checkpoint`, `body_weight`/`body_symptom`, `mind_checkin`, `people_interaction` — `archived_at IS NULL`/`IS NOT NULL` distinguishing open/completed) and the Phase 9/10A integration caches (`CalendarEventCache` filtered to selected calendars and to-day's date; `GoogleHealthDailySummary` for BODY trends). No new data model was invented for tasks/deadlines/checkpoints. Every line carries a `source_ref` (e.g. `record:{id[:8]}`, `calendar_event:{id[:8]}`). Output is `OutputSection(title, lines: OutputLine(text, source_ref))`, serialized to `RoutineRun.output_json`. Morning Briefing always includes Calendar/LIFE/PATH/BUILD; BODY/MIND/PEOPLE are appended only when explicitly selected (`SENSITIVE_DOMAIN_SLUGS`). Weekly Review requires explicit opt-in for every domain, sensitive or not. Evening Check-in is a fully static 4-prompt template with no data pulled and no model call; Bernardo's own typed answers are recorded via a dedicated endpoint straight into that run's `responses_json` — never promoted into a Phase 4 memory automatically.

**Single-flight and failure handling**: identical pattern to §9d — one `threading.Lock` per routine type, a collision recorded as `"skipped"`, bounded exponential backoff on failure, and `run_routine` wraps content assembly in a generic try/except so a routine bug can never crash the scheduler.

**Schema** (migration `0010_routines.py`, forward-only, 0001-0009 untouched): `routine_schedules` (seeded `enabled=0` for all three types) and `routine_runs`.

**Restore behavior**: `import_service._disable_all_routine_schedules` forces every routine schedule to `enabled=0, next_due_at=NULL` immediately after every restore, mirroring `_disable_all_integration_schedules` — routine configuration (cadence, timezone, selected domains) and historical `RoutineRun` outputs are preserved, only the live schedule state is forced off.

**"Discuss with Jarvis"**: deliberately not a new backend route. The frontend reuses the existing `POST /api/conversations/{id}/turns` endpoint (via the existing `createConversation`/`sendTurn` functions) to send a routine's rendered text into a real conversation turn — the only path in this feature that can reach a model, and only on explicit user action, going through the same context-boundary/domain-scoping machinery as any other conversation turn.

**API/UI**: `GET`/`PUT /api/routines/{routine_type}/schedule`, `POST /api/routines/{routine_type}/run`, `GET /api/routines/{routine_type}/history`, `POST /api/routines/runs/{run_id}/responses` — all explicit local UI actions, not Phase 8 proposals (same reasoning as §9d's schedule config). `RoutineCentre.tsx` (reachable from the top bar and command palette) shows, per routine: enable toggle, constrained schedule controls, domain-selection controls, last/next run, status, latest output (explicitly labeled "generated locally — not a model response"), history, "Run now," and "Discuss with Jarvis" (whose reply is explicitly labeled "Jarvis (model response)" to keep the two visually and textually distinct).

Following the cinematic-HUD pass (§9f), a further refinement addressed feedback that the result still read as a generic "AI-generated futuristic dashboard" rather than a deliberately designed instrument. This is a presentation change only — the description text itself still comes straight from `GET /api/domains`, never rewritten or fabricated. Idle nodes lost their periodic "breathing" glow animation entirely (now genuinely static until interacted with); hover/focus now also briefly show a short per-node "connector" stub (`.domain-connector`, oriented via the same angle used to place the node) and brighten the shared `.orbit-path` ring via a `:has()` selector, rather than redrawing a bespoke line to the core per node.

A separate small `⌘K`-labeled button keeps the command palette's existence obvious without relying on users already knowing the shortcut.

**Motion system**: two new tokens (`--motion-control: 190ms`, `--motion-panel: 240ms`) and a single easing curve (`--ease-hud: cubic-bezier(0.22, 1, 0.36, 1)`) now drive every interactive control's hover/active/focus transition and every panel's entrance animation, replacing a mix of ad hoc durations. Hover always uses `translateY(-1px)` plus a targeted `border-color`/`box-shadow`/`background` transition (never `transition: all`); pressed/active always uses `scale(0.98)`; disabled controls explicitly zero both transform and box-shadow so they never appear to lift or glow. `prefers-reduced-motion` continues to zero every animation/transition duration globally (§9f) — this required no additional reduced-motion-specific code for any of the new motion.

**Deterministic local UI-command layer** (`frontend/src/commands/`): a small, model-independent, allowlisted command registry and parser (`registry.ts`) shared by two surfaces — the Command Palette (typed input, `resolveCommand` prop) and `DomainView`'s voice transcript handling (spoken input, checked before a transcript is ever sent to Jarvis as a conversation turn). `parseCommand(text)` is a pure function with no model/Hermes involvement: it normalizes the input and matches it, by exact string equality after stripping a leading navigation verb, against fixed alias tables for the six domains and six centres (e.g. "health area" → BODY, "career space" → PATH) — deliberately exact-match rather than substring/contains matching, since a "contains" match would risk misreading an ordinary conversational sentence that happens to end in a domain word (e.g. "...affecting my body") as a navigation command instead of sending it to the model. It returns one of four outcomes:
- `navigate` — a safe destination (a centre, a domain, home, back, or the command palette itself). Executed immediately.
- `focus_control` — a phrase naming a specific sensitive control (currently the Google Calendar/Health connect, disconnect, enable-writing, and automatic-sync controls in Integrations Centre, matched by requiring all relevant keywords present regardless of word order, e.g. "connect google calendar" and "google calendar connect" both resolve). This only navigates to Integrations Centre and briefly highlights the exact control (`commands/highlight.ts`, matching a `data-command-target` attribute already present on those specific elements) — it never clicks, toggles, or submits anything. The UI explicitly labels this as "shows, does not activate."
- `blocked` — any other phrase combining a mutating/destructive verb (connect, disconnect, delete, approve, execute, sync now, etc.) with a recognizable system noun (calendar, health, action, skill, backup, document, etc.), or a positional-selection phrase ("press the second button") — refused with an explanation, never executed and never silently forwarded anywhere.
- `none` — anything else. The Command Palette's static action list still applies as before; `DomainView`'s voice path falls through unchanged to the existing "send this transcript to Jarvis as a conversation turn" behavior (CLAUDE.md §8's ordinary-conversation-by-default rule is untouched).

Execution (actually calling `setShow*`/`setSelectedSlug`) lives in `App.tsx` (`navigateToTarget`/`runParsedCommand`), since only `App` owns that navigation state — `registry.ts` and `highlight.ts` know nothing about React state and are fully unit-testable in isolation (`commands/registry.test.ts`, 52 cases covering every alias, every sensitive control, every blocked-phrase category, and — explicitly — that ordinary conversational sentences containing a mutating verb or a domain word are never misread as a command). A voice command outside an active domain conversation became reachable in D79 (§9j), once Home/Centre push-to-talk existed at all — the parser's "none" result there routes to the ambient general conversation as an ordinary question, rather than the domain-choice prompt this paragraph originally anticipated.

## 9j. Global Jarvis interaction: one shared voice hook and a controller-owned command hierarchy (Phase 6, D79)

**Shared voice state machine** (`frontend/src/hooks/useVoiceCapture.ts`): the voice state machine previously duplicated between `DomainView.tsx` and `GeneralConversation.tsx` (§9i) is now one hook, `useVoiceCapture({ guard, onSystemCommand, submitTurn })`, wrapping `usePushToTalk` internally. `guard()` (checked once a recording completes, before transcription starts) returns `true` to proceed, `false` to abort silently (e.g. no conversation selected), or a string to abort with that string as a real voice error — this is exactly the gate DomainView/GeneralConversation each already had inline. `onSystemCommand` receives any of the registry's four actionable kinds (`navigate`, `focus_control`, `safe_action`, `confirm_required`); the hook itself never executes one — it only classifies and hands off, so the caller (always `App.tsx`'s `runParsedCommand`, the same function the Command Palette already used) is the single place real navigation/execution happens. `submitTurn` is whatever the caller's own conversation-turn mechanism is. Every fix already proven in D78 (the `stopPushToTalk` state-clobber guard, the TTS-element race fix — set `ttsAudioEl` state only after `.play()` resolves, never merely after `.src` is assigned) now lives in this one hook instead of two parallel copies. `App.tsx` instantiates exactly one additional `useVoiceCapture` — call it the *ambient* instance — active only while `ambientVoiceEligible` (Home or a Centre page; false while a domain conversation or the general conversation, each owning their own instance, is mounted; also false on a diagnostic page). Because starting a capture only ever happens from the currently-eligible instance's own Space handler, there is never more than one live `getUserMedia`/`MediaRecorder` session regardless of how many `useVoiceCapture` instances exist in the tree.

**The ambient general conversation**: Home/Centre voice questions have no "selected conversation" the way `GeneralConversation.tsx` lets you pick one, so `App.tsx` lazily creates-or-reuses a single real general conversation (`fetchGeneralConversations()` → find by a fixed title, `"Quick questions (voice)"`, else `createGeneralConversation(...)`) the first time it's needed, memoizing the in-flight promise so a second question asked before the first request resolves reuses the same creation rather than racing a duplicate. It is an ordinary row in the `conversations` table with `domain_id = NULL` — visible in `GeneralConversation.tsx`'s own conversation list like any other — not a hidden or special-cased record. **Command safety — three tiers, all controller-owned** (`frontend/src/commands/registry.ts`): `SafeAction` (`sync_provider`, `retry_connection`, `run_routine`) and `ConfirmAction` (`disconnect_integration`, `export_data`) are two new `ParsedCommand` result kinds alongside the existing `navigate`/`focus_control`/`blocked`/`none` (§9g). ## 9l. A real shared-element View Transition for Home→domain navigation, and removing a rectangular panel behind JarvisCore (Phase 6, D90)

Real-Mac visual inspection found two genuine defects the container passes above could not have caught (one visual, one from a CSS-cascade interaction that has nothing to do with any test fixture): a rectangular panel visible behind the Home `JarvisCore` ring assembly, and a manually-simulated (`setTimeout`-based, up to 220ms) "grow then wait then cut" domain-navigation delay in place of real motion. See `docs/DECISIONS.md` D90 for the full root-cause account, exact numbers, and verification detail — this entry records only the resulting architecture.

**`frontend/src/transitions/domainViewTransition.ts`** is the new single entry point for every Home↔domain navigation path (pointer click, keyboard activation, number shortcuts, a typed/spoken command naming a domain, and the reverse "Back to Jarvis"). It wraps a real `document.startViewTransition()` call, tagging whichever DOM node carries a matching `data-domain-transition-slug` attribute on each side (Home's `DomainNode` button, or the new `frontend/src/components/DomainEmblem.tsx` in a domain view's own header) with one shared `view-transition-name` so the browser morphs one into the other; when no matching node exists on either side (e.g. a command fired from a Centre page), no name is assigned and the browser's own default root crossfade is the fallback — never a second, bespoke "plain navigation" code path. Falls back to an immediate, undelayed `commit()` with no `document.startViewTransition` call at all when the API is unsupported or `prefers-reduced-motion: reduce` is set, and latches against re-entrant double-activation since the API's own callback runs in a microtask rather than synchronously.

**Choreography** lives entirely in `index.css` under `@media (prefers-reduced-motion: no-preference)`: a tuned `::view-transition-group(jarvis-domain-shared)` duration/easing for the morph itself, and a customized `::view-transition-old(root)`/`::view-transition-new(root)` (a replacement reveal keyframe adding a short upward-translate-plus-fade, delayed slightly so it visibly follows the identity morph) for everything else on the page — deliberately not a bespoke per-node dimming animation, since the old root snapshot fading out already covers "the other five nodes, the orbit, and the core all dim together." A `.no-view-transitions` class, set once at startup (`main.tsx`) via feature detection, gates a small CSS-only fallback crossfade for browsers without the API.

**The square's root cause** was a CSS specificity gap, not a structural HTML issue: `.jarvis-hud-interactive`'s own `background: none; border: none;` reset was being overridden by a higher-specificity global `button:not(.primary):not(.back-button):not(.domain-button):not(.push-to-talk-button)` base rule that had simply never been taught to exclude it — fixed by adding `:not(.jarvis-hud-interactive)` alongside the three existing exclusions, the same pattern `.domain-button`/`.push-to-talk-button` already relied on.

**Verification**: `docs/DECISIONS.md` D90.

## 16. Phase 12B: briefing continuity — stable identity, content fingerprint, and acknowledge/snooze (D87)

Extends §15's assembler in place — no second briefing engine, no duplicated priority logic. See `docs/DECISIONS.md` D87 for the complete narrative; this section is the durable architectural record.

**Two identifiers per candidate**: `BriefingItem.id` is the *stable identity key* — represents the same underlying concern across time and must never embed volatile state (a correction from §15: `integration_sync:{provider}:error/stale` collapsed to `integration_sync:{provider}`; `google_health:no_data`/`google_health:{summary_id}` collapsed to the fixed slot `google_health:freshness`; `routine_run:{run_id}` became `routine_run:{routine_type}` — in each case the volatile part moved into the fingerprint instead). `BriefingItem.fingerprint` is a 16-hex-char SHA-256 digest (`_fingerprint()`) over a small, explicit, per-source set of already-normalized fields — documented inline at each construction site, never a raw provider payload/secret/token. Calendar/LIFE/PATH fingerprints deliberately include the item's `category` (NOW/NEXT), so an item becoming more urgent is itself a `changed` classification (the brief's explicit requirement); integration-sync and BODY-freshness fingerprints deliberately exclude exact timestamps/day-counts, so a still-broken condition doesn't reclassify as `changed` on every tick.

**Persistence** (migration `0013`, forward-only, `0001`-`0012` untouched):
* `briefing_snapshots` — bounded (`SNAPSHOT_RETENTION_PER_CONSUMER=200`, trimmed on insert), deduped (`SNAPSHOT_DEDUPE_WINDOW_SECONDS=60` — an identical digest within the window reuses the existing row), tagged with `consumer` (`home`/`morning_briefing` — the actual comparison-baseline lineage) and an audit-only `trigger`.
* `briefing_item_states` — the Home-only per-identity ledger (`stable_key` unique, `status` active/resolved, `current_fingerprint`, cached `last_title`/`last_subtitle`/`last_category`/`last_link_target`, `reopened_count`). The Morning Briefing routine (`app/routine_service.py::run_routine`) never reads or writes this table — it only records its own lightweight `briefing_snapshots` row (`consumer="morning_briefing"`, digest derived from its own rendered line text, no per-item fingerprinting) immediately after a successful run. This is what makes "a background routine run must not silently consume Home's baseline" a structural guarantee, not a documented intention.
* `briefing_acknowledgements` / `briefing_snoozes` — presentation-preference tables keyed to an exact `(stable_key, fingerprint)` pair, each carrying a frozen `*_snapshot` display-text copy taken at write time.

**Classification** (`_reconcile_ledger`, run over the complete un-capped candidate set — priority-cap churn can never manufacture a false `new`/`resolved`):
* no ledger row → `new`.
* ledger row `status=='resolved'` → `reopened` (`reopened_count` increments).
* ledger row `status=='active'`, fingerprint unchanged → `ongoing`.
* ledger row `status=='active'`, fingerprint changed → `changed`.
* an `active` row absent from this pass's candidates → `resolved`, **only if** that identity's `source_type` evaluated successfully this pass (see below) — otherwise untouched.

A freshly-resolved identity gets exactly one synthesized display item (`tone="neutral"`, lowest WATCH priority — "shown sparingly" falls out of the state machine, not a separate display rule) before the ledger row settles into `resolved` and stops appearing at all.

**False-resolution protection** (`_gather_candidates`): every source's query runs inside its own try/except, producing a `SourceEvaluation(source_type, ok, detail)` regardless of any other source's outcome. A failed source contributes zero candidates this pass *and* is excluded from the resolution check above — its previously-active identities are left exactly as they were, never marked resolved, never stripped of acknowledgement/snooze history. `include_body=False` and "domain not found yet" are modeled as successful no-op evaluations, never conflated with a failure.

**Acknowledge/snooze — presentation only, structurally enforced** (`acknowledge_item`/`snooze_item`/`restore_item`/`is_suppressed`): the fingerprint used is always the ledger's *current* one, resolved server-side — a client can never acknowledge/snooze a stale or fabricated version of an item. Suppression is a lookup on the exact `(stable_key, fingerprint, status='active')` triple, so a fingerprint change automatically stops any existing acknowledgement/snooze from applying, with no explicit invalidation step anywhere. Snoozing accepts only the fixed `1h`/`4h`/`tomorrow_morning`/`1w` enum (validated by both a Pydantic `Literal` and the service function); `tomorrow_morning` is computed DST-safely (`_tomorrow_morning_utc`, mirroring `routine_service._next_occurrence_utc`'s wall-clock-first construction). `expire_due_snoozes` runs at the start of every `assemble_home_briefing` call. Neither function creates a Phase 8 `ActionProposal` or touches any capability — this is real-only presentation state.

**API** (`app/routers/briefing.py`, same route family as §15): `GET /api/briefing/home?trigger=home_view|home_refresh` (both share the `home` baseline), `GET /api/briefing/history?consumer=&limit=`, `POST /api/briefing/items/{stable_key}/acknowledge|snooze|restore`. `{stable_key}` is always one of the pre-existing safe identity strings — never a raw title, provider payload, or token.

**Frontend** (`frontend/src/components/BriefingStrip.tsx`): a second badge dimension (NEW/CHANGED/ONGOING/RESOLVED/REOPENED) alongside the existing NOW/NEXT/WATCH category badge, with its own color mapping (cyan=new/resolved, amber=changed/reopened, quiet/no-fill=ongoing) — independent of the existing tone/severity colors, never color alone. Per-item Acknowledge and a native-`<details>` Snooze disclosure sit beside (never nested inside) the navigate button. An unobtrusive, closed-by-default "Acknowledged & snoozed" history lists suppressed items with a Restore action and one explicit "this only changes what's shown, never the underlying record" sentence. "Discuss with Jarvis" now includes each item's change-state label in the same quoted-reference-data text already governed by `app/context_builder.py`'s prompt-injection boundary.

## 19. Phase 12D: Unified Recall and Provenance — deterministic local search across all six domains, reusing FTS5 wherever it already exists (D98)

Gives Bernardo one fast, trustworthy place to search everything Jarvis has stored locally and open the exact underlying source. Explicitly **not a model feature** — see the module docstring of `app/recall_service.py` and D98's own "why no model/embeddings" section for the full reasoning; this section is the durable architectural record.

**Hybrid indexing strategy, chosen only after inspecting every write path** (never a first-choice default): `app/recall_service.search()` merges three independently-scored FTS5 sources rather than building one giant duplicate index. Memory items keep using the pre-existing `memory_fts` (`app/fts_service.py`, Phase 4) unchanged; document chunk text keeps using the pre-existing `document_fts` (`app/document_fts_service.py`, Phase 9) unchanged; every other source type indexes into one new table, `recall_fts` (migration 0016), via `app/recall_index_service.py`. This was the deliberate alternative to duplicating already-indexed content a second time (which would create exactly the "index drift" risk the phase was asked to prevent) and to building nine separate small FTS tables (which would multiply the write-path surface for no real benefit, since `recall_fts` already scales to millions of rows as one FTS5 table).

**The nine source types indexed into `recall_fts`** (`RECALL_SOURCE_TYPES`): `conversation` (title), `message` (content, domain resolved from its conversation), `structured_record` (a flattened rendering of its JSON payload's string/number fields), `domain_summary` (the current version's content), `document` (filename only — chunk *content* stays in `document_fts`, never duplicated), `calendar_event` (title/description/location, always domain `life` by the same convention `briefing_service.py`/Mission Control already use), `action_proposal` (`reason`/`expected_effect`/`error_summary` only — never `arguments_json`, `confirmation_token`, or `result_json`), `routine_run` (`reason` plus the documented plain-text `output_json.sections[].lines[].text` values only — never the raw JSON shape), and `mission_control_session` (`title`/`completion_note`/`what_changed_note`/`source_title_snapshot`).

**Deliberately excluded, with reasons recorded rather than left to a reader's guess**: Google Health metrics/sessions (purely numeric telemetry with no natural free-text search value — the spec explicitly allows omitting this); `BriefingSnapshot` (stores only a digest/count, no real text at all) and `BriefingItemState` (its title/subtitle always duplicate an already-independently-indexed source — Calendar/structured-record/action-proposal — and re-indexing it on every Home-view load would add write-path load for zero new information, the exact case the spec's own "where they add information not already represented by their source" clause is written to exclude); per-event `ActionAuditEvent` detail rows (the proposal's own `reason`/`expected_effect`/`error_summary` already carry the meaningful text; granular audit-trail forensics were judged out of scope for a search feature); Mission Focus pins (not named in the product spec's own source list, and every field on a pin already duplicates its underlying source); `Skill`/`SkillVersion` (likewise not in the spec's source list).

**Domain resolution is normalized to a slug at write time, never a domain_id at read time**: every `recall_fts` row stores `domain_slug` (nullable — `NULL` means "global/system", the explicitly documented classification for content with no single owning domain: a general conversation, a domain-less manual mission, an action proposal with no `domain_id`, every routine run). This is what makes every query-time domain filter a plain `WHERE domain_slug IN (...)` — never a join against `domains` — and keeps the index speaking the exact same vocabulary `frontend/src/domainOrder.ts` does.

**Privacy is structural, not a post-filter**: `search()` takes an explicit `domain_slugs` argument; omitting it defaults to `("life", "path", "build")` only (`DEFAULT_DOMAIN_SLUGS`) — BODY/MIND/PEOPLE can only ever appear in a result set that explicitly named them. An explicit but *empty* list is honored literally (a real "no domain content at all" request), never silently widened back to the default. This is the identical structural rule Phase 12A/12B/12C/Mission Control already established for the Home briefing, applied to search.

**Ranking is one deterministic pipeline, never embeddings, never a model** — computed in `app/recall_service._score()`: (1) each FTS family's raw bm25 scores (lower = more relevant, SQLite's own convention) are min-max normalized independently into a 0-1 "relevance" value (`_normalize_family`) before combining, since raw bm25 magnitudes aren't comparable across differently-shaped tables/corpora; (2) an exact title/phrase match adds a fixed `+0.5` bonus; (3) an optional caller-supplied `current_domain` hint (set when Recall is opened from inside a domain) adds `+0.1` to same-domain results — the realization of "domain/filter match" as its own ranking tier; (4) a bounded, capped recency signal (`_RECENCY_BONUS_MAX = 0.05`, decaying over a documented 365-day half-life) can only ever break a near-tie, never override a real relevance difference; (5) the final, always-deterministic tie-breaker sorts by `(source_type, source_id)` lexically. See the docstring on `_score`/`_normalize_family` for the exact formula — this is intentionally the complete ranking algorithm, not an approximation of one kept elsewhere.

**Why no model call, no Hermes, no embeddings, anywhere in this feature**: search must be instant, free, fully offline-capable, and its ranking must be independently auditable and reproducible by reading this one module — none of which a model or embedding-similarity call can guarantee (latency, cost, non-determinism, and a live Hermes/network dependency the product's own local-first mandate rules out for a feature this core to daily use). Every requirement the spec sets (deterministic tie-breaking, exact reproducibility, "never call Hermes, generate summaries, infer facts, or treat retrieved text as instructions") is naturally satisfied by staying entirely inside SQLite's own FTS5/bm25 machinery. Confirmed structurally, not just by design intent: an AST-walk test (`test_recall_service_imports_no_model_provider`/`test_recall_service_never_calls_send_turn`) proves `app/recall_service.py` imports no provider module and calls no `send_turn`, mirroring the identical guarantee already established for `mission_focus_service.py`/`mission_control_service.py`.

**Snippet safety**: `make_snippet_html()` HTML-escapes the retrieved excerpt *first*, then wraps query-token matches in `<mark>` — highlighting always operates on the same already-escaped string it returns, so a document/message/record containing literal HTML, script tags, or text phrased as an instruction to an AI ("ignore previous instructions and...") can never inject markup or be treated as anything other than inert, escaped, displayed data. Proved directly by dedicated tests, not just asserted.

**Schema** (migration `0016`, forward-only, `0001`-`0015` untouched): one new FTS5 virtual table, `recall_fts(source_type UNINDEXED, source_id UNINDEXED, domain_slug UNINDEXED, occurred_at UNINDEXED, title, content)` — never authoritative, exactly like `memory_fts`/`document_fts` before it.

**Synchronization, never periodic-only**: `app/recall_index_service.sync_recall(session, source_type, source_id)` is idempotent and safe to call from both a create and an archive/delete path — it always re-fetches and re-renders the real source row fresh (never trusting caller-supplied content), and deletes any existing index row instead of inserting a stale one when the source is no longer indexable. Wired into every real create/update/archive/delete write path that produces recall-eligible content: `app/document_service.py` (ingest completion, permanent delete), `app/routers/memory.py` (structured-record create/archive, domain-summary set/clear), `app/routers/general.py`/`app/routers/domains.py` (conversation creation), `app/routers/conversations.py`/`app/turn_service.py` (message creation, both the direct-post and turn-orchestrated paths), `app/integration_service.py` (each Calendar event upserted during a sync), `app/action_service.py` (proposal creation, and re-synced when `error_summary` is set on execution failure), `app/routine_service.py` (each `RoutineRun` created), and `app/mission_control_service.py` (`start_mission`/`complete_mission`/`abandon_mission`). `sync_recall`/`remove_recall` both check `sqlite_master` for the table's existence before touching it (via `_recall_fts_table_exists`, never a try/except around the real DML, which would otherwise poison the caller's whole transaction on a DBAPI error) — this is what keeps them safe to call even from service-layer code exercised against a schema revision older than 0016, a real scenario `test_migration_0005.py`'s existing historical-data-preservation test exposed live during this implementation.

**Backfill and repair**: `rebuild_recall_index()` (`app/recall_index_service.py`) drops and fully repopulates `recall_fts` from every current ground-truth table — the backfill path for an installation upgrading from before migration 0016, and the manual repair path if the index is ever suspected stale. Run automatically, once, at backend startup only when the table is found empty (`app/main.py`'s lifespan, mirroring every other Phase 9-12 startup-sweep pattern — never blocks or fails startup on error) — never a periodic background resync, since every relevant write path already calls `sync_recall` directly. Also reachable manually via `POST /api/recall/rebuild`.

**Availability is always re-checked fresh at read time, never trusted from the index**: `_resolve_availability()` re-queries the real source row for every result on the current page (bounded by `limit`, not by index size) and reports `available: false` / `"Source unavailable"` truthfully rather than silently dropping a result whose underlying row has since been deleted — defense in depth against any missed sync path, proved by a test that deletes a source row without calling `remove_recall` and confirms the stale index row still surfaces as an honest "unavailable" result rather than vanishing or fabricating content.

**Resilience**: each of the three FTS family queries (`memory_item`, `document_chunk`, the `recall_fts` families) is independently wrapped — one family's failure is reported in `RecallSearchResult.partial_failures` and never zeroes out the other two families' real results. A malformed/pathological FTS query (unbalanced quotes, bare operators, excessive length, null bytes) reuses `app.fts_service.sanitize_fts_query` (Phase 4's own established safe-tokenization pattern — every token becomes a literal quoted phrase, OR-joined) and never raises past `search()`.

**API** (`app/routers/recall.py`): `GET /api/recall/search` (bounded `limit`≤50, `offset`, explicit `domains`/`source_types`/`include_global`/`current_domain` filters) and `POST /api/recall/rebuild` — every request is read-only except the explicit rebuild action; no search ever mutates application state.

**Frontend**: see `docs/DECISIONS.md` D98 for the Recall Centre UI, its command-registry phrasings, and its keyboard shortcut.

**Verification**: full backend suite 749/749 (78 new: `test_recall_index_service.py` 27, `test_recall_service.py` 34, `test_recall_api.py` 9, `test_migration_0016.py` 3, `test_recall_export_restore.py` 2, `test_recall_performance.py` 3), `ruff check` clean. See D98 for frontend verification counts.

**Boundary respected**: no routine or integration-schedule change; no OAuth/credential/Keychain/provider mutation; no Hermes toolset/configuration change; no model call anywhere in indexing, sync, or search; no sub-agent introduced; no Home orbit/canonical-glyph redesign; no Git operation.

## 20. Phase 12E: Source-Grounded Research Workspace — evidence collection and cited briefs built entirely on top of Phase 12D Unified Recall (D99)

Lets Bernardo collect explicitly selected evidence from Recall into a named workspace, classify it (supporting/contradicting/contextual/unresolved), attach his own notes, and produce a versioned, cited brief from only that selected evidence — never unrestricted web research, never an autonomous agent, and never a second search/indexing engine. See the module docstrings of `app/research_service.py` and `app/models_research.py`, and CLAUDE.md's own Research Centre durable-rule block, for the full reasoning; this section is the durable architectural record.

Two small, deliberate extraction points were added to `recall_service.py` itself (not duplicated into `research_service.py`) so both features share one implementation: `resolve_source_snapshot(session, source_type, source_id)` (a freshly-resolved, server-side title/content/domain/occurred-at snapshot for any of the eleven Recall source types — reuses `recall_index_service`'s nine existing renderers plus the two inline `memory_item`/`document_chunk` resolutions `search()` itself already had) and `resolve_availability(session, source_type, source_id)` (a public wrapper around the same `_resolve_availability` helper `search()` uses for every result). Retrieved text — including anything phrased as an instruction to an AI — is only ever displayed, inert data; it is never executed, never alters a system prompt, and never triggers a tool, command, or mutation, structurally proved by the AST-walk tests described below.

Restore never triggers regeneration or a model call (nothing in `import_service.py`'s restore path touches `research_service`); a restored workspace's evidence/notes/brief versions are read back exactly as exported, and a source that no longer exists post-restore is truthfully reported unavailable by the same fresh `resolve_availability` check every other read already uses — never silently dropped from a historical citation.

## 21. Phase 12F: Evidence-Based Decision Room — transparent, evidence-grounded decisions built on Phase 12D Recall and Phase 12E Research (D101)

Completes Recall → Research → Decide → Focus. Lets Bernardo weigh a real decision — options, criteria, evidence, assumptions/risks/unknowns — with a deterministic, inspectable score, and later review how it actually turned out. Jarvis supports the decision; it never makes it. See the module docstring of `app/decision_service.py`, and CLAUDE.md's own Decision Room durable-rule block, for the full reasoning; this section is the durable architectural record.

**Reuse, not duplication**: `app/decision_service.search_decision_evidence()` calls `app.recall_service.search()` directly, exactly as `app.research_service` already does — no parallel query/ranking implementation. `add_evidence`/`import_research_evidence` reuse `recall_service.resolve_source_snapshot`/`resolve_availability`/`resolve_link_target` and `recall_service.make_snippet_html` for frozen, escaped display snapshots, the identical helpers Research (§20) established. `import_research_evidence` additionally lets a decision pull in an existing `ResearchEvidence` row by reference (preserving its `research_evidence_id` for provenance) rather than re-searching Recall for the same source.

**Privacy is an INTERSECTION, never a union, when a Research workspace is linked**: `_effective_domain_slugs(session, decision)` returns the decision's own `included_domain_slugs`, filtered down to only those also present in the linked workspace's `included_domain_slugs_json` (`decision_service.py:160`). Linking a workspace can only narrow or preserve evidence-discovery access, never widen it — a decision cannot gain access to a domain via a workspace link that its own policy didn't already include, and vice versa. `_domain_allowed` independently re-validates every evidence add against this effective set server-side, even though `search_decision_evidence` already scopes discovery the same way — defense in depth against a direct/malformed API call, mirroring Research's own `_domain_allowed` pattern (§20).

**Data model** (migration `0018`, forward-only, `0001`-`0017` untouched): eight new tables. `decisions` (title, optional `description`/`domain_id`, optional `research_workspace_id`, `included_domain_slugs_json`, `status` draft/evaluating/decided/reopened/superseded/abandoned, `review_date`, `cost_of_delay_note`, `info_confidence` 1-5, `reversibility` easily_reversible/hard_to_reverse/irreversible, `supersedes_decision_id`/`superseded_by_decision_id`, `abandoned_at`/`abandoned_reason`). `decision_options` (name, benefits/costs/risks, optional per-option `reversibility`, `status` active/eliminated/chosen, `rank`). `decision_criteria` (name, `weight` 1-5, `rank`). `decision_assessments` (one row per option×criterion pair actually scored — `score` 1-5, optional `note`; an unscored pair simply has no row, never a row with a null/zero placeholder). `decision_evidence_links` (a typed `source_type`/`source_id` pointer — the same twelve-value vocabulary Recall's eleven types plus `"decision"` itself, since a decision may cite another decision; optional `research_evidence_id` for provenance when imported from a linked workspace; frozen `title_snapshot`/`snippet_snapshot`/`occurred_at_snapshot`; `stance` supporting/contradicting/contextual/unresolved; `status` active/removed). `decision_factors` (assumption/risk/unknown register — `kind`, `content`, `status` open/resolved, `resolution_note`/`resolved_at`). `decision_brief_versions` (UNIQUE `decision_id`+`version_number` — `source` deterministic/model, `status` ok/invalid_citations, `sections_json`, `citations_json`, `validation_json`, `model_meta_json` only for `source='model'`). `decision_final_versions` (UNIQUE `decision_id`+`version_number` — `selected_option_id`, `rationale`, `decision_confidence` 1-5, `decided_at`; only ever inserted by `decide()`, never updated). `decision_outcome_reviews` (`decision_final_version_id`, `what_happened`, `intended_outcome_achieved`/`confidence_was_appropriate`/`would_decide_same_again` — each an independent nullable boolean, never forced — `lessons_learned`). A partial unique index, `uq_decision_evidence_links_active_source` on `(decision_id, source_type, source_id) WHERE status='active'`, gives real database-level evidence-add idempotency, mirroring migration 0014's/0017's identical pattern.

**Scoring is a pure, deterministic function, never a database query or a model judgment**: `compute_score_breakdown(options, criteria, assessments)` (`decision_service.py:690`) takes plain in-memory lists and returns a `ScoreBreakdown` (`__slots__`-based, no DB access, no randomness). A total is a plain integer sum of `score × weight` over every *assessed* (option, criterion) pair for that option; a missing assessment contributes nothing and is reported separately (`missing_criterion_ids`/`missing_criterion_names`), never defaulted to zero or any other value — this is what makes "unassessed" structurally distinguishable from "scored zero." Only non-eliminated options are ranked. The tie-break is deterministic (`-total_score` then `option_id` ascending — never insertion order). **Sensitivity warnings** are computed by recomputing every option's total with each criterion excluded in turn (`_total_for(..., excluded_criterion_id=...)`) and flagging any criterion whose removal would change the #1-ranked option — a plain, auditable "is this result actually driven by one weight" check, not a statistical sensitivity model.

**Deterministic brief** (`generate_deterministic_brief`): never calls a model. Citation numbers are assigned 1..N via `_citation_order_evidence` — evidence ordered by stance (`_STANCE_ORDER`: supporting, contradicting, contextual, unresolved, mirroring Research's own `CLASSIFICATION_ORDER`), then by when it was added, then by id — the one ordering both the deterministic brief and the critique's evidence packet share. The brief's `sections_json` always includes a `score_breakdown` section plus options/criteria/evidence/factor summaries, and a `missing_info_warnings` list (e.g. an incomplete assessment matrix, a tied ranking) — never silently omitted.

**Model boundary** (`draft_critique_with_model`): exactly one `provider.send_turn()` call, identical structural shape to Research's `draft_brief_with_model` (§20) — no tools enabled (the `AgentProvider` protocol accepts only `system_prompt`/`messages`/`timeout`), no autonomous follow-up call, no hidden Recall/Research search. The evidence packet (`_evidence_packet`, capped at `_MAX_EVIDENCE_FOR_CRITIQUE = 40`) plus decision context (`_decision_context_text` — title, description, options, criteria, score breakdown, open factors) are appended only to the **user** message; `_MODEL_SYSTEM_PROMPT` is a fixed string that never incorporates decision or evidence content, so nothing evidence contains can rewrite Jarvis's own instructions. **Structurally, not just verbally, incapable of deciding anything**: the critique is persisted as a `DecisionBriefVersion` with `source="model"` — a completely different table from `DecisionFinalVersion` — so a critique can never set status, choose an option, or create a final version, confirmed by a dedicated test (`test_critique_never_creates_a_final_version_or_changes_lifecycle_status`). On any failure — no evidence, no options, or a `ProviderError` — nothing is persisted: the decision and every existing version are left completely untouched (`test_model_failure_leaves_decision_and_prior_versions_untouched`).

**Citation validation, server-side**: identical mechanism to Research (§20) — every `[N]` bracket the model's response contains is split into valid (present in the evidence packet actually supplied) and invalid; an invalid number is preserved verbatim in the displayed text but recorded in `validation_json` and flips `status` to `invalid_citations`, never silently dropped (`test_invalid_citation_number_is_flagged_not_silently_dropped`). `citation_reads` always re-resolves each citation's `available`/`unavailable_reason`/`link_target` fresh via `recall_service.resolve_availability`/`resolve_link_target` at read time.

**Lifecycle** (`decision_service.py:223`-`404`): `create → start_evaluating → decide` is the common path; `decide()` requires an active (non-eliminated) option and a non-empty rationale, creates a new `DecisionFinalVersion` (never overwrites a prior one — reopening and deciding again always adds another version), and sets `status="decided"`. `reopen()` is valid from `decided` or `abandoned`, resetting `abandoned_at`/`abandoned_reason` only when reopening from `abandoned` — a real bug (the `was_abandoned` check running *after* the status mutation, so the reset branch could never fire) was found and fixed proactively during this pass's own test-writing, before any test run exposed it live. `supersede()` links two decisions bidirectionally (`supersedes_decision_id`/`superseded_by_decision_id`) without touching either one's own options/evidence/history. `abandon()` is valid from any editable or decided status. Only `DECISION_EDITABLE_STATUSES = ("draft", "evaluating", "reopened")` allow adding/changing options, criteria, evidence, or factors — a decided/superseded/abandoned decision is read-only for those, though briefs and outcome reviews remain addable.

**Export/restore/restart**: identical mechanism to Research (§20) — no per-table export/import code needed, since Jarvis's export snapshots the whole SQLite database file. Restore never triggers regeneration or a model call. A source that no longer exists post-restore is truthfully reported unavailable by the same fresh `resolve_availability` check every other read uses, never silently dropped from a historical citation (`test_removed_source_after_restore_reports_unavailable_without_erasing_citation`). An ordinary backend restart preserves every decision/option/criterion/assessment/evidence/factor/brief/final-version/outcome-review row exactly as it was (`test_ordinary_restart_preserves_decision_data`) — there is no in-flight timer or session state to force into an interrupted status here, unlike Mission Control (§18), since every Decision Room mutation is already a discrete, immediately-committed action.

**API** (`app/routers/decisions.py`): decision CRUD (`POST`/`GET`/`PUT /api/decisions[/{id}]`), research-workspace linking (`PUT .../research-workspace`), lifecycle (`POST .../start-evaluating`, `.../decide`, `.../reopen`, `.../supersede`, `.../abandon`), evidence discovery (`GET .../evidence/search`, read-only, delegates to Recall), options/criteria/assessments/evidence/factors CRUD, score breakdown (`GET .../score-breakdown`), briefs (`GET .../briefs[/{id}]`, `POST .../briefs/deterministic`, `POST .../briefs/critique`), final versions and outcome reviews (`GET .../final-versions`, `GET`/`POST .../outcome-reviews`), and a global `GET /api/decisions-calibration-summary`. Every mutating route uses `PUT`/`POST` only, never `PATCH`/`DELETE`, matching the backend's restricted CORS `allow_methods` and every prior Phase 8-12 router's convention (`POST .../{criterion_id}/remove` returns `204` rather than using `DELETE`, exactly like Research's evidence-remove route).

## 22. Native macOS Packaging — Stage 1 (Tauri 2 shell + PyInstaller sidecar) (D104)

Turns the existing dev-mode application into a real `/Applications/Jarvis.app`, without changing the frontend's or backend's own product behavior. Private, single-Mac use only — no notarization, no paid Developer account, no DMG/updater/App-Store distribution; there is no pending "Stage 2."

**Layout**: `frontend/src-tauri/` — `Cargo.toml`, `tauri.conf.json`, `src/lib.rs` (app setup, tray menu, window lifecycle), `src/sidecar.rs` (process ownership/health-gating), `entitlements.plist`, `offline-dist/offline.html` (the window's initial content), `binaries/jarvis-backend-aarch64-apple-darwin` (the built sidecar, Tauri's `externalBin` convention). `backend/packaging/entrypoint.py` (frozen-process entrypoint: runs Alembic migrations, then `uvicorn.run`) and `backend/packaging/jarvis_backend.spec` (PyInstaller onefile spec — bundles `alembic/`, `alembic.ini`, and the built `frontend/dist` as `frontend-dist`).

**Same-origin frontend serving, unchanged from dev mode**: the native window's URL is the sidecar's own `http://127.0.0.1:8000/` — `app/main.py`'s existing static-mount logic (already used by `scripts/jarvisctl.sh`) serves the frontend from there. `_resolve_frontend_dist_dir()` (`app/main.py`) is frozen-aware: under `sys.frozen`, it resolves `sys._MEIPASS / "frontend-dist"` (PyInstaller onefile's per-run extraction directory) rather than assuming `Path(__file__)` still points at the real source tree — a regression caught and fixed with two focused tests (`test_frontend_dist_dir_resolves_from_meipass_when_frozen_onefile`, `test_frontend_dist_dir_falls_back_to_executable_dir_when_frozen_without_meipass`) before it ever shipped.

**Startup sequencing** (`sidecar.rs::start`, spawned as a background thread from `lib.rs::setup`): probe `GET /api/health` on 127.0.0.1:8000 — a genuine Jarvis JSON body means reuse (never touch that process's lifecycle, `SidecarState.owned_child` stays `None`); a non-Jarvis response on that port is reported as a real conflict, never silently adopted; no response at all means spawn-and-own, with `cwd` set to the real `backend/` source directory (baked into the binary at compile time via `build.rs`'s `JARVIS_BACKEND_DIR` — an explicit, documented Stage-1-only assumption: this one Mac, this one repo checkout, no distributed installer). Health is then polled every second for up to 30s; on success the window `navigate()`s to the real origin and is revealed; on failure (or a mid-poll port conflict) a truthful error state is shown on `offline.html` instead, via a `jarvis://sidecar-status` event (state/message) the page listens for — never a silently-hung invisible window.

**Two real defects found via actual process inspection (`ps`, `lsof`) on real hardware, not code review**:
- *Undrained stdio deadlock*: `tauri-plugin-shell`'s `Command::spawn()` always creates OS pipes for the child's stdout/stderr; the event receiver must be drained for the life of the process — Alembic's first-run migration log alone is large enough to fill the kernel pipe buffer, after which the child blocks on `write()` forever with zero visible error. Fixed by permanently forwarding every `CommandEvent` on a `tauri::async_runtime::spawn`ed task.
- *Orphaned sidecar on Quit*: `CommandChild::kill()` sends `SIGKILL` to the tracked pid — for a PyInstaller **onefile** sidecar that pid is the bootloader stub, not the real unpacked interpreter process it supervises. SIGKILL gives the bootloader no chance to relay anything (PyInstaller's bootloader forwards SIGTERM, not SIGKILL, to its child — documented upstream behavior), so the real process was found reparented to `launchd`, still bound to port 8000, breaking every later launch's reuse probe. `shutdown_owned_backend` now sends SIGTERM to the tracked pid first, waits up to 2s, escalates to SIGKILL only if needed, then independently re-checks whoever is still bound to port 8000 and kills it only if its executable path is an exact match for the bundled sidecar binary — verified cleanup, not assumed.

**A third real defect, found later (D107/D109) via a genuine incident on the real Mac, not code review**: `backend/packaging/entrypoint.py` never called `multiprocessing.freeze_support()` — required for any PyInstaller-frozen executable that might use Python's `multiprocessing` module with the `'spawn'` start method (macOS's default since Python 3.8). Without it, when something inside the frozen app spawns a multiprocessing worker (most likely `ctranslate2`'s own worker-process handling during `faster-whisper`'s `WhisperModel` construction — see §8a-i), the "worker" re-invocation falls through to this same script's own `main()` instead of the intended tiny bootstrap, re-running the entire FastAPI lifespan (migrations, the Phase 10 scheduler's startup catch-up) from scratch — a self-sustaining, roughly-once-per-second respawn loop, each cycle hitting the real Keychain again on the real Mac. Fixed with the one standard line, `multiprocessing.freeze_support()`, as the first statement in `entrypoint.py`'s `if __name__ == "__main__":` block. Verified against the exact original trigger condition (a temporary, never-shipped diagnostic hook reconstructing `WhisperModel` eagerly during startup): zero respawns over 45s with the fix, versus 39+ respawns in under a minute without it. See D109.

**Lifecycle**: `tauri-plugin-single-instance` (registered before every other plugin, per Tauri's own requirement) focuses the existing window on a second launch attempt rather than spawning a duplicate. `WindowEvent::CloseRequested` calls `prevent_close()` + `hide()` — closing the window never stops scheduled integration syncs/routines, which keep running in the still-alive backend. `tauri::RunEvent::Reopen` (macOS Dock-icon click on a running, windowless app) restores it. The tray menu: Open/Hide/System Status (currently equivalent to Open — the frontend is a single-URL SPA with no client routing, so this is an honest interim choice, not a fabricated deep link)/Sync Integrations (direct `POST` to both providers' sync endpoints)/Export Portable Jarvis Backup/Restore from Jarvis Export…/Reveal Jarvis Data Folder (§23)/Launch at Login (a `CheckMenuItem`, `tauri-plugin-autostart`, defaults to disabled and nothing enables it automatically)/Quit. Quit and the native Cmd+Q/Dock▸Quit path both route through the same `shutdown_owned_backend` (called both from the tray's own menu-event handler for immediacy, and from `RunEvent::ExitRequested`/`Exit` so every real exit path is covered identically).

**Signing — a stable local identity, not ad-hoc, not a real Developer ID**: ad-hoc signing (the default with no configured identity) gives every rebuild a different CDHash, which Keychain's per-item "Always Allow" ACL keys off of for ad-hoc-signed code — so every rebuild re-prompted for the real Calendar/Health Keychain items. Fixed with one self-signed local certificate ("Jarvis Local Dev," `codeSigning` EKU only, 10-year validity), created via `openssl` + `security import ... -T /usr/bin/codesign` + `security add-trusted-cert -p codeSign` (scoped to the login keychain only — no System-wide trust change), only after Bernardo's explicit approval of the exact written proposal. `tauri.conf.json`'s `bundle.macOS.signingIdentity` pins it so the designated requirement is keyed off the certificate (stable across rebuilds) rather than the binary's content hash. A second, layered problem surfaced once a real identity was configured: Tauri's signing step then applies **hardened runtime**, whose default Library Validation rejected the bundled `Python.framework` and every native extension module (none of them carry this identity — confirmed via a captured `different Team IDs` code-signature error and a stack sample genuinely blocked inside `SecItemCopyMatching`). `entitlements.plist` sets `com.apple.security.cs.disable-library-validation` and `com.apple.security.cs.allow-unsigned-executable-memory` — safe and correct specifically because this build is never notarized or distributed; documented explicitly as the wrong choice for a hypothetical future Developer-ID build.

**Verification**: installed `/Applications/Jarvis.app` (90MB, arm64) opens with no Chrome/Safari/manually-entered URL; exactly one instance and one owned sidecar; backend healthy in 8-16s; real Google Calendar/Health stayed connected with unchanged scopes across every relaunch (no OAuth screen); window close→Dock reopen works; Quit leaves port 8000 free with zero orphaned processes (re-verified after the fix); Hermes stayed loopback-only, zero enabled toolsets throughout; `scripts/jarvisctl.sh` untouched and still functions as the dev/recovery fallback. Backend: 2 new focused regression tests for the frozen frontend-dist path; full backend suite (946/946) and full frontend suite (433/433) plus a clean production build re-run once, since implementation code changed.

## 23. Cross-Mac Portability: Guarded In-App Restore (D105)

A bounded extension of Phase 2's existing export/restore implementation (§2-era `app/export_service.py`/`app/import_service.py`), added directly after §22 at Bernardo's explicit requirement that `Jarvis.app` remain portable between his Macs — the app bundle is application code only, all persistent context stays in `JARVIS_DATA_DIR`, and installing/rebuilding/replacing/moving the app must never touch it. This was already structurally true (nothing in §22 changes how `app/config.py` resolves the data directory, and the sidecar reuses the exact same real directory the dev-mode backend already used); what was added is a convenient, safe way to actually move a snapshot between two Macs.

**No new archive format, no second restore implementation**: `POST /api/restore` (`app/routers/data_management.py`) and the native Data Management "Restore from Jarvis export" flow both call the exact same `import_service.restore_archive()` the CLI (`jarvis-cli restore`) already used — same manifest/checksum/schema validation, same forced-disconnected integrations, same forced-disabled integration/routine schedules, same interrupted-focus-session handling, same rollback-on-failure. The API endpoint requires an explicit `confirm` field to overwrite a target that already has data, mirroring `--confirm` exactly (`422` on an invalid archive, `409` without confirm on a non-empty target).

**Live-database restore, made safe**: restoring over the *same running process's own* database (the actual scenario the native UI performs) requires releasing that process's held file handles before the file underneath them is replaced. The endpoint calls `request.app.state.engine.dispose()` immediately before `restore_archive()` runs — this only closes the shared `Engine`'s pooled connections; the `Engine`/`sessionmaker` objects themselves (and every reference already held to them, including `SchedulerRuntime`'s) are never rebuilt or reassigned, so every later checkout transparently opens the now-restored file at the same path. Verified with a real regression test (`test_restore_endpoint_restores_over_the_live_database`) that restores over the test client's own live database mid-suite and then confirms the same process keeps serving `/api/health` and `/api/domains` correctly afterward — not merely that the restore call itself returned `200`.

**New surface**: `GET /api/data-dir` — the resolved, absolute `JARVIS_DATA_DIR` path (non-secret; already shown as UI copy). Backs both Data Management's own display of the real path and the native tray's "Reveal Jarvis Data Folder" (fetches this endpoint, then shells `open <path>`). Data Management's former CLI-only restore module (a deliberate Phase 2 safety choice) is replaced with a guarded flow: choose file → immediate validation → an explicit "I understand this replaces this Mac's current Jarvis data" checkbox gates the Restore button → result reports exactly what was restored and that integrations/schedules are now disabled pending review. The tray's "Restore from Jarvis Export…" item deliberately never performs the restore itself — it only brings Jarvis to the front, matching §22's own "System Status" precedent — the guarded flow lives entirely in Data Management.

## 24. Post-Stage-1 real-use stabilization: seven defects found by actually using the installed app (D106)

Not a new phase or a Stage 2 — a bug-fixing pass against `/Applications/Jarvis.app` after §22/§23 shipped, triggered entirely by Bernardo's own real daily use rather than by a planned acceptance drill. Every defect below was found on real hardware, not in code review; each was root-caused before being fixed.

**Icons**: dock/app icon set regenerated from Bernardo-supplied artwork — the source had ~54px of transparent padding around already-rounded art, which macOS 11+ reads as "not full-bleed" and backs with its own plate, producing a visible double border; fixed by cropping to the content bounding box and rescaling to a full-bleed 1024×1024 canvas. The menu-bar tray icon was completely invisible with Tauri's `icon_as_template(true)` set on this icon/OS combination (empirically confirmed broken across repeated rebuilds, root cause not pursued further given time cost) — fixed by loading the icon without that flag and using the sharper @2× (36px) source for crispness.

**OAuth "Connect" opened nothing, silently**: root cause was `window.__TAURI__` (the JS/IPC bridge) never being present at all on the app's real content — it's injected only into content loaded from Tauri's own trusted origin (`offline.html`), never into content reached via `window.navigate()` to what Tauri treats as an external origin, `http://127.0.0.1:8000`, even though it's localhost (see §22's same-origin serving). A custom Tauri command (`open_external_url`) was fully wired — capability ACL, `build.rs` registration, verified against the generated schema files — and still never received a single invocation, confirmed via Rust-side logging showing zero calls despite the backend's own `/connect` endpoint succeeding repeatedly. Fixed by moving browser-opening entirely server-side: `app/routers/integrations.py`'s `_open_in_system_browser()` calls `subprocess.Popen(["open", url])` directly from `start_oauth`, right before the endpoint returns — works identically whether the frontend is loaded by the native app or by `jarvisctl.sh`'s dev-mode browser workflow, and needed zero Tauri IPC. The now-dead `open_external_url` Rust command and `frontend/src/nativeShell.ts`'s `openExternalUrl` were removed entirely rather than left as unreachable code.

**Repeated Keychain re-prompting on every integration sync**: two-layered. (1) A one-time real-Keychain-ACL configuration gap on Bernardo's own Mac, resolved by him directly in Keychain Access.app (adding `jarvis-backend` to "Always allow" per item, after a controlled temporary "Allow all applications" diagnostic test confirmed the mechanism) — not a code change. (2) The structural cause — `keyring.set_password()` deletes and recreates the Keychain item on every token write, resetting the item's ACL every time an OAuth token is refreshed — was root-caused in this session but a first `SecItemUpdate`-based fix attempt failed with `errSecParam` against a disposable test item and was reverted rather than deployed unproven. **This was later fixed properly in D108**: the `errSecParam` failure turned out to be a `CFStringRef`-vs-`CFDataRef` type mismatch in the update call, not a fundamental limitation — see `app/keychain_update.py` above and D108 for the full fix, proven again against a disposable item before being applied to the real write path.

**Diagnostic ring animation** (`app/routers/integrations.py`'s `_callback_page`): the OAuth callback page's ring now spins continuously on success and does a slow, repeating turn-and-hold-and-return on failure (`diag-ring-spin`/`diag-ring-turn-stop` CSS classes, `animation-iteration-count: infinite` on both — an earlier version played the failure animation once, which Bernardo corrected), both respecting `prefers-reduced-motion`.

**A stuck "VOICE ERROR" screen with no way to leave except quitting the app**: two-layered, both fixed. (1) All three Escape-key handlers (`App.tsx`, `DomainView.tsx`, `GeneralConversation.tsx`) only treated `voiceState === "listening"` as cancelable, never `"error"`. (2) Even after fixing that, `useVoiceCapture.ts`'s own `cancel()` had an independent hard gate requiring `voiceState === "listening"`, so calling it from `"error"` was silently a no-op regardless of what called it — the real root cause. Covered by a genuine (unmocked) regression test exploiting jsdom's natural lack of `getUserMedia` (`frontend/src/useVoiceCapture.test.ts`).

**Microphone access silently failing before ever reaching TCC** — Jarvis never appeared in System Settings → Privacy & Security → Microphone at all, and `getUserMedia` failed with a generic, uninformative message (a bare `catch {}` in `usePushToTalk.ts` had been discarding the real `DOMException`). Fixing the error message first (surfacing `err.name`/`err.message`) revealed the real error: `NotAllowedError: ... not allowed by the user agent or the platform`, a platform-level block, not a user denial. Root cause: `entitlements.plist` (§22) disabled Library Validation but never declared `com.apple.security.device.audio-input` — required under hardened runtime for `getUserMedia` to ever reach TCC at all; without it, WKWebView refuses the request outright, before any prompt exists and before Jarvis is TCC-registered at all. Fixed by adding the entitlement; verified present in the signed binary via `codesign -d --entitlements :-` before deployment, then confirmed working end-to-end (real permission prompt, real transcription) on the real Mac.

**The voice-error overlay had no reliable way to dismiss, and a related state bug made a *stale* error reappear**: `VoiceCaptureOverlay.tsx` is `pointer-events: none` in every state except `"error"` (preserving push-to-talk's release gesture reaching the real control underneath in every other state) — the error state now accepts a click anywhere on it, plus a real focusable "Dismiss" button, both calling the same `cancel()`. A related bug found alongside it: navigating away from Home only *masked* the ambient (Home-level) voice overlay's display — its underlying `useVoiceCapture` state, held in `App.tsx`, kept whatever it was, `"error"` included — so returning to Home later could show the same stale error again with no new failure behind it. Fixed with an effect that calls `ambientVoice.cancel()` the moment Home/Centre eligibility (`ambientVoiceEligible`) turns false. A secondary side effect was also found and fixed: the error overlay briefly accepting pointer events blocked the domain node underneath the cursor from ever receiving its own pointer-leave, leaving its hover tooltip frozen open — `Home.tsx` now explicitly clears `hoveredSlug` via a new `voiceActive` prop whenever the overlay is showing.

**Holding Space too long scrolled the whole app**: root cause was `event.preventDefault()` being called only on the *first* Space keydown (gated behind `!event.repeat`) in all three push-to-talk listeners (`App.tsx`, `DomainView.tsx`, `GeneralConversation.tsx`) — the OS's auto-repeat keydown events that fire continuously on a long hold were never prevented, so the browser's native "Space scrolls the page" action activated once repeat kicked in. Fixed by calling `preventDefault()` on every Space keydown unconditionally while still gating the actual `start()`/`startPushToTalk()` call behind `!event.repeat` so capture is never restarted mid-hold.

**Background fade during any active voice state**: `.voice-capture-overlay`'s backdrop deepened from `rgba(5, 3, 8, 0.55)` to `rgba(4, 2, 7, 0.9)`, at Bernardo's request, so the domain ring and briefing strip genuinely fade away behind the core/waveform rather than staying fully legible underneath a faint scrim.
