# Jarvis — Roadmap

This document derives from and is subordinate to `CLAUDE.md` (the authoritative project profile). If anything here conflicts with `CLAUDE.md`, `CLAUDE.md` wins.

Each phase must end with automated tests, manual acceptance checks, and a concise report. Do not implement later phases early. Stop at the boundary of the requested phase — do not continue into the next phase without a new prompt.

## Revised execution order (Bernardo, post-Phase-5)

The phases below keep their original numbers — nothing is renumbered — but are now **implemented** in this order:

**Phase 7 → Phase 8 → Phase 9 → Phase 10 → Phase 6 → Phase 11**

Reason: the existing functional (unpolished) frontend already supports development and testing of the remaining V1 behaviours — macOS launching, permissions/hooks/skills, read-only integrations, and sub-agents. The production HUD (Phase 6) is deliberately pushed to just before final hardening (Phase 11), so it is built once, against stable V1 behaviour, rather than rebuilt as those behaviours land. See `docs/DECISIONS.md` D40.

## Local transcription latency: diagnose-first pass; one fix kept, one reverted after a real incident (D107)

A focused diagnostic pass, not a feature or model change, on `/Applications/Jarvis.app`'s push-to-talk latency. Measured on the real M2 Pro before touching anything: warm `faster-whisper` transcription (`base`/`cpu`/`int8`, unchanged) already ran 0.6-1.0s for short clips — reasonable, left alone. **Kept**: `POST /api/voice/transcribe` no longer blocks the event loop during inference (`asyncio.to_thread`). **Attempted, then fully reverted**: eagerly loading the whisper model at backend startup instead of on the first push-to-talk turn — deployed to the real installed app and found to trigger a severe, reproducible runaway process-respawn loop (constructing the model during the app's own startup lifespan causes the whole frozen binary to re-execute itself roughly once per second, indefinitely, each cycle re-running the integration scheduler — this is what caused a real "infinite" Keychain-prompt incident on Bernardo's Mac). Fully backed out, not merely disabled — eager preload was not reintroduced even after the underlying defect was fixed (see below). See `docs/ARCHITECTURE.md` §8a-i and `docs/DECISIONS.md` D107 for the full incident account and isolated-reproduction evidence. Real-hardware push-to-talk latency-feel verification against the rebuilt installed app is Bernardo's own direct action (no agent session can operate a real microphone) and remains outstanding.

## Packaging fix: `multiprocessing.freeze_support()` (D109)

The packaging-level defect D107 disclosed but explicitly left unfixed was root-caused and fixed at Bernardo's explicit request: `backend/packaging/entrypoint.py` was missing the standard `multiprocessing.freeze_support()` call every PyInstaller-frozen executable needs when anything inside it might use Python's `multiprocessing` module with the `'spawn'` start method (macOS's default). Missing it meant a spawned worker process (triggered by `ctranslate2` during `WhisperModel` construction) fell through to re-running the app's entire startup instead of the intended worker bootstrap — the actual mechanism behind D107's runaway-loop incident. Fixed with one line; verified against the exact original trigger condition via a temporary, never-shipped diagnostic hook (zero respawns over 45s with the fix, vs. 39+ in under a minute without it), then deployed and reconfirmed stable on the real Mac. See `docs/ARCHITECTURE.md` §22 and `docs/DECISIONS.md` D109.
